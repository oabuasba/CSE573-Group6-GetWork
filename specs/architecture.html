GetWork — Architecture

The master spec for GetWork, a two-way resume and job matcher. Every agent and developer reads this before working on any feature.

Status: DraftUpdated: 2026-11-10Course: CSE 573, Group 6, Project 3Authors: Omar Abuasba, Prathyush Vasa
getwork

Overview

GetWork matches in both directions. Given a resume, it returns the top-k job postings. Given a posting, it returns the top-k candidates. Related skills get partial credit through a skill taxonomy built from the corpus: skill embeddings are clustered, and each document's skills are grouped under their cluster names before the document is embedded. A conversational agent then explains each match in terms of shared and related skills.

Research question

Does structuring resumes and postings around a corpus-generated skill taxonomy improve two-way matching over keyword and embedding baselines, while producing explanations that candidates and recruiters can act on?

Domain: software engineering and adjacent
Directions: resume→jobs, job→candidates
Language: Python backend, React UI
Structuring LLM: ASU Voyager-hosted model or a local Qwen server, model and backend id logged per record (ADR-11, ADR-13)
Timeline: 8 weeks
Team: 2 authors, joint work

Motivating example

A posting asks for React. A resume lists single-page apps built in Vue. They share no keywords, so keyword matching scores them at zero. Plain embeddings may rank the pair highly but can't say why. In GetWork both skills fall in the Front-end cluster, so the serialized documents share that label and move closer together, and the agent can point to the related skill.

Components

There are two phases. The offline build phase runs once over the corpus and writes artifacts (structured records, taxonomy, vectors). The query phase loads those artifacts in a FastAPI service. The evaluation harness reads the same artifacts and rankings.

Pipeline

The pipeline has 8 steps (ADR-2). Steps 1–6 run once on the corpus. Steps 7–8 run per request. A newly submitted document goes through steps 2, 5, and 6 before matching. Classical steps (rules, statistics, non-neural ML) group, rank, and provide baselines. Modern steps (LLMs, neural embeddings) build the representations. Hover or tab to a step for detail.

1 · Filter (classical)Drop empty, short, duplicate, non-English, or corrupted docs; keep software postings by title, with industry as a secondary check
filtered resumes + postings
2 · Structure (both)A Voyager-hosted LLM extracts title, skills, experience (with durations), and education; a separate alias table canonicalizes skills (JS→JavaScript)
structured records, canonical skills
3 · Select skills (both)Count canonical skills across both corpora; keep the top 1,000; embed each one on its own
skill vectors
4 · Cluster (classical)UMAP, then a grid over DBSCAN, HDBSCAN, and k-means; best silhouette under a noise cap, then manual review
skill taxonomy
5 · Re-label (both)Look up known skills; noise goes to "Other"; the LLM handles unseen skills and incomplete docs
cluster-labeled records
6 · Embed docs (modern)Serialize as title, level, and clustered skills; one vector per document; B2 uses the same text without cluster labels
document vectors (Full, B2)
7 · Two-way match (classical)S = R̂Ĵᵀ; top-k by row (jobs for a resume) or column (candidates for a job); B1+ scored in parallel
ranked matches
8 · Explain (modern)LangGraph agent with tools for similarity search, cluster lookup, and side-by-side comparison

Key design points

TopicRule
Structuring passesPass 1 runs on every filtered document. Pass 2 (step 5) calls the LLM only for skills not in the taxonomy and for documents whose extraction looks incomplete.
Incomplete extractionA document is reprocessed from raw text if it has fewer skills than the corpus 10th percentile, or if fewer than half its skills are in the taxonomy. This also catches implied skills ("built CI pipelines" implies DevOps).
Noise skillsSkills marked as noise in clustering have no cluster. They go under Other, so they still count for exact matches but earn no partial credit.
Two vector spacesThe skill space (step 3) is used only for clustering. The document space (step 6) is used for matching. The two connect only through step 5.
Experience levelPostings use their listed level. Resumes get a level derived from the total years of experience extracted in pass 1.
Reasoning modeReasoning stays off in both structuring passes (reasoning_effort="none", temperature 0).

Evaluation

Evaluation compares three systems with matched inputs, in both directions, using LLM-judge labels that authors check on a human-labeled subset. This section follows the presentation, which supersedes the proposal (ADR-1, ADR-8, ADR-9).

Systems compared

SystemScoringInputs
B1+Skill Jaccard + title overlap + seniority match; weights tuned on the dev setSkills, title, experience level
B2Cosine on embeddings of documents serialized without cluster labelsSkills, title, experience level
FullCosine on embeddings of cluster-aware documentsSkills, title, experience level

B1+ vs. B2 isolates the embeddings. B2 vs. Full isolates the taxonomy.

Labeling stages

  1. Development: 10 resumes + 10 postingsTwo LLM judges label the pooled pairs. The authors review judge rationales on 20–30 pairs and fix the rubric. Repeat until judge κ ≥ 0.6, and tune the B1+ weights here. The rubric is frozen after this stage.
  2. LLM-labeled test: 100 resumes + 100 postingsThe top-10 from B1+, B2, and Full are pooled, shuffled, and shown without system names (TREC-style pooling). Two judges from different model families, neither used in the pipeline or agent, see raw text. When they disagree, the lower label wins. Final results use these labels.
  3. Human check: 10 resumes + 10 postings from the test setBoth authors label the same pooled top-10 pairs, about 400, blind and with no adjudication. The judge counts as a third annotator. Report author–author κ, each judge's κ against each author, Kendall's τ of the system order, and the metric gaps between systems (e.g. Full − B2 nDCG@10) under judge labels and under each author's labels.

Labels are 0 not relevant, 1 partial, 2 relevant, judged on skills and seniority. A clear seniority mismatch in either direction caps the label at 1. The pool is the software postings, capped at a fixed random sample of 5,000. Resumes are sampled stratified by their first occupation label. For posting queries, each posting is ranked against all filtered resumes.

Fallback when judges disagree with humans: revise once on half, report on the other half

Human–judge κ is the mean of the judges' κ against each author. If human–judge κ < 0.6 while author–author κ ≥ 0.6: (1) split the human set into two halves of 5 resumes + 5 postings; (2) use the first half to diagnose disagreements (each judge alone, the lower-label rule, the raw-text input, the rubric); (3) revise once and relabel the full test set; (4) report human–judge κ only on the untouched second half. If judges are still clearly worse than authors after one revision, the human-labeled queries become the primary results and the judge results become secondary. If both κ values are low, the task itself is subjective, and both are reported side by side.

Questions and metrics

QuestionMeasureExpected
Are the top matches relevant?P@5, P@10, MRR (only label 2 counts as relevant), nDCG@10, per direction; under judge labels and each author's labelsFull > B2 > B1+ under both authors
Do clusters reflect real roles?ARI between k-means (k=10) over per-resume cluster-count profiles and first occupation label, vs. the same on raw skill countsMatches raw skills with far fewer dimensions
Do related skills get partial credit?Rank drop of original top-10 postings after a same-cluster (React→Vue) vs. a different-cluster (React→Java) substitution in the structured recordFull: smaller drop for same-cluster; B1+: equal drops; B2 in between
Are explanations faithful?Judge rating 1–5 on faithfulness and usefulness for each test resume's top match; automatic hallucination rate; 10 reviewed by handHigh rating, few hallucinations
Are the gaps real?95% bootstrap CIs; paired randomization test on per-query scores, judge labelsp < 0.05

Cluster quality is also reported as the silhouette score (cosine, in the original embedding space, clustered skills only) plus the noise fraction, along with the fraction of retained skills found in only one corpus. A hallucination is a skill named in an explanation that appears in neither document's final skill set. Cluster names don't count.

Fixed by the project docs

IdContractDefinition
CC-1Structured recordEvery document, resume or posting, becomes one record with title, skills (list of strings; canonical after alias mapping, see CC-2 and the built alias-table feature; the structurer stores skills as written, structurer D-4), experience (entries with durations), and education (entries). It is validated by one shared Pydantic model; invalid LLM output is regenerated. Entry fields, decided in the structurer spec (D-1 to D-3): experience[] = {role, company, duration_months}, education[] = {degree, field, institution}, plus years_experience. The model is ModelOutput in src/getwork/structure/schema.py.
CC-2Canonical skillEvery skill string passes through the alias table before any counting, lookup, Jaccard, or serialization (e.g. JS→JavaScript, k8s→Kubernetes). Built in alias-table: getwork.alias.table.AliasTable.canonical / canonicalize_list map a skill through a normalized key (NFKC, whitespace collapse, casefold, trailing .,;: stripped). Downstream stages read skills only from the canonical records (getwork.alias.apply.read_canonical), which carry skills_raw and alias_table_version, and call single_alias_version to refuse mixed versions (CC-12). The display spelling of a key ignores all-caps forms of 5 or more letters when another form exists (so HTML, JSON, REST survive; JAVASCRIPT does not). Matching is exact on the key; the LLM proposer only drafts rows for human review. Version folding (ADR-22, spec alias-and-naming-v2): versioned and edition spellings of a product on a reviewed list (version_families.csv: Windows 7, Windows Server 2019, SQL Server 2012, Python 3.9) are entered into the table at build time as the versionless canonical, so the exact-key lookup is unchanged; numbers that are not versions (Cisco 3750, ISO 27001, S3) are never folded.
CC-3TaxonomyA mapping from canonical skill to cluster name, built from the top 1,000 skills. Noise and unassigned skills map to Other.
CC-4Document serializationFull: title, experience level, then skills grouped under cluster names, e.g. Front-end: Vue, CSS; Cloud: AWS, with an Other group. B2: the same title, level, and skills with no cluster labels. Resumes and postings use the same format and model.
CC-5Vectors and scoresEvery document vector is L2-normalized at write time, so cosine is an inner product. Scores come from S = R̂Ĵᵀ. Rows are resumes, columns are postings.
CC-6System idsExactly B1+, B2, Full in every ranking, label, and metric artifact.
CC-7Relevance labelAn integer in {0, 1, 2}. A seniority mismatch caps it at 1. For P@K and MRR only 2 counts as relevant. Judge disagreements resolve to the lower label.
CC-8Blind labelingLabeling UIs and judge prompts never show the system that produced a pair. Authors never see judge labels during labeling.

ADR-2 · Two-phase, eight-step pipeline

Date: 2026-11-07. Context: structuring and clustering are expensive and corpus-wide. Matching and explanation run per query. Decision: Steps 1–6 form an offline build phase that writes artifacts. Steps 7–8 form the query phase. New documents go through steps 2, 5, and 6. Alternatives rejected: structuring on demand at query time, which can't support corpus-wide taxonomy building or evaluation. Consequences: artifacts are the hand-off between phases and need stable formats (core contracts).

Superseded by ADR-11

ADR-3 · Self-hosted Qwen3-8B on vLLM for structuring

Status: superseded by ADR-11 for where the model runs and which model. The rule that output is JSON validated against a Pydantic schema and regenerated on failure stays in force.

Date: 2026-11-07. Context: pass 1 needs tens of thousands of LLM calls. Decision: Host Qwen3-8B on ASU Sol GPUs, with Google Colab as a fallback, and serve it through vLLM's batched serving. Thinking mode is off. Output is JSON validated against a Pydantic schema and regenerated on failure. Alternatives rejected: a rate-limited external API, which has variable cost and is less reproducible. Consequences: structuring cost is fixed and reproducible. The structuring code depends on Sol GPU availability.

Accepted

ADR-4 · One embedding model and a shared document space

Date: 2026-11-07. Decision: Qwen3-Embedding-4B, via sentence-transformers, embeds both single skills (skill space, used for clustering) and serialized documents (document space, used for matching). Resumes and postings share one model and one format. Alternatives rejected: separate encoders per side, which would break the shared space needed for two-way retrieval. Consequences: any new document must be embedded with the same model and serialization.

Accepted

ADR-5 · Cluster-aware serialization gives partial credit

Date: 2026-11-07. Decision: Documents are serialized with skills grouped under cluster names (CC-4). Noise skills go under Other. The B2 baseline uses identical text without the labels. Alternatives rejected: scoring cluster overlap separately from the embedding, which would add a second scoring path and remove the clean B2-vs-Full ablation. Consequences: the B2–Full gap measures the taxonomy's contribution.

Accepted

ADR-6 · Taxonomy selection procedure

Date: 2026-11-07. Decision: Keep the top 1,000 canonical skills by count across both corpora. Reduce with UMAP, then grid-search DBSCAN (ε, minPts), HDBSCAN (minimum cluster size), and k-means (k, as reference). Among configurations under a maximum noise fraction, pick the highest mean silhouette, computed with cosine distance in the original embedding space on clustered skills only. Then review the clusters by hand. Alternatives rejected: picking by silhouette alone, since well-separated clusters aren't necessarily meaningful. Consequences: selection has a human step, so the chosen configuration and cluster names must be saved as an artifact.

Accepted

ADR-7 · Retrieval by normalized matrix product

Date: 2026-11-07. Decision: Cosine similarity via unit-normalized vectors and NumPy inner products. Top-k jobs for a resume come from its row of S, and top-k candidates for a job from its column. Alternatives rejected: a vector database or ANN index, which is unnecessary at this scale (~30k × ≤5k). Consequences: retrieval is exact and deterministic.

Accepted

ADR-8 · B1+ is a matched-input lexical baseline

Date: 2026-11-07. Context: the proposal's B1 saw skills only, while B2 and Full also saw title and experience level, so any B1 gap mixed vocabulary with seniority. Decision: B1+ combines skill Jaccard over final skill sets, title overlap, and seniority match, with weights tuned on the dev set. Alternatives rejected: skills-only B1, which confounds the comparison. Consequences: each comparison changes one factor. The exact formula is still open (Q-2).

Accepted

ADR-9 · Three-stage labeling protocol, balanced across directions

Date: 2026-11-07. Decision: Dev (10 + 10), then an LLM-labeled test set (100 + 100), then a human check (10 + 10, ~400 pairs), as described in Evaluation. Two judges come from different model families, neither used in the pipeline or agent. Judges read raw text, the lower label wins, and the rubric is frozen after dev, with the revise-on-half fallback. Alternatives rejected: the proposal's 100 + 20 split and 20 consensus pairs, which were too small to validate the judges and unbalanced across directions. Consequences: about 7 hours of human labeling per author in week 6, and the labeling UI must support blind, per-author labeling.

Accepted

ADR-10 · Explanation agent on LangGraph via ASU CreateAI

Date: 2026-11-07. Decision: A LangGraph agent takes a matched resume and posting and explains the match using tools for similarity search, cluster lookup, and side-by-side comparison. Its model is reached through CreateAI's OpenAI-compatible API. Alternatives rejected: self-hosting the agent model, which is unnecessary because agent traffic is interactive and low-volume. Consequences: the agent model is chosen in config. It must differ from both judge models.

Status: superseded by ADR-21 for where the model is served (Voyager by default instead of CreateAI). The LangGraph agent, its tools and the rule that the agent model differs from both judge models stay in force.

Accepted

ADR-11 · Pass-1 structuring runs on the ASU Voyager API behind an LLMClient protocol

Date: 2026-11-07. Context: ADR-3 chose self-hosted Qwen3-8B on vLLM and rejected a rate-limited external API. ASU Research Computing now offers Voyager, an OpenAI-compatible API on ASU-run hardware, with no cost and no published numeric rate limits (queue wait 5 minutes then 503, per-minute token budget then 429, 4 to 8 workers recommended). Voyager does not list Qwen3-8B. The user will run the structuring loop on their own machine with their own API key. Decision: (1) Pass-1 structuring is run by one resumable script, structurer, which talks to the model only through an LLMClient protocol (src/getwork/llm/client.py). (2) The first implementation uses the openai SDK against Voyager. A vLLM/Sol backend can be added later without changing the loop, prompt, or schema. (3) The model id has no default. It comes from .env or --model, and every output record stores model, prompt_version, and schema_version. (4) A model different from Qwen3-8B is acceptable. (5) The ADR-3 rule stays: output is validated against the Pydantic schema and regenerated on failure. Alternatives rejected: keeping vLLM-only (needs Sol GPU access the user has not arranged, and blocks structuring until it exists); hard-wiring Voyager into the loop (makes a later backend change a rewrite and forces tests to mock HTTP); defaulting a model id in code (a retired or replaced model would then change the dataset silently). Consequences: runs are hours long and can hit 429s, so the loop must resume, back off, and log failures per record. Reproducibility now depends on the logged model id and on Voyager keeping that model, and the model id is a reported experimental setting. The structuring model is part of the pipeline, so it should not be one of the judge models (ADR-9 keeps judges out of the pipeline); ADR-10 separately keeps the agent model different from the judges, and neither ADR constrains the structuring model beyond that. Agents never hold the key or call the API (CC-10).

ADR-12 · Downstream stages are trial-first, artifact-driven CLIs with offline tests

Date: 2026-11-07. Context: the structurer ran on 100 resumes and 100 postings (data/structured_trial); the full corpus (28,842 resumes, 8,423 postings) comes later. Real model runs are user-run (CC-10) and the final taxonomy depends on the full corpus. ADR-13 · A local Qwen server is a second LLM backend behind LLMClient

Date: 2026-11-07. Context: ADR-11 moved structuring to Voyager behind an LLMClient protocol and anticipated other backends. The user has an RTX 5070 (12 GB) and wants to run the LLM steps locally, for example Qwen. Decision: the existing openai-SDK adapter serves local OpenAI-compatible servers (vLLM, Ollama, llama.cpp) by configuration: --backend {voyager,local} or LLM_BACKEND, with LOCAL_LLM_* variables (key optional). Connection refusal is fatal for local, transient for Voyager. Every record carries a backend field, which joins the provenance tuple, so resuming across backends raises ProvenanceMismatchError; per-backend defaults for workers, reasoning effort and response schema; validation with feedback retries is the structured-output guarantee everywhere. All LLM steps (alias proposal, cluster naming, unseen-skill assignment, re-extraction) use one make_client factory. Alternatives rejected: a dedicated client per server (three version-sensitive adapters), an in-process model (torch in the structurer path, untestable offline). Consequences: ADR-11 stands (this extends it); the recommended local model is a 4-bit Qwen3-8B with a reduced input limit; the LLM server and the embedding model cannot share the 12 GB card, so they run one after the other. Spec: local-llm-backend.

ADR-14 · Embeddings go through an EmbeddingClient protocol; Qwen3-Embedding-4B runs locally

Date: 2026-11-07. Context: ADR-4 fixed Qwen3-Embedding-4B via sentence-transformers. The user runs it on the local RTX 5070 (12 GB); ASU Voyager also offers embedding models. Tests must never load a multi-gigabyte model or reach the network. Alternatives rejected: importing sentence-transformers in each stage (untestable offline, GPU handling repeated); Voyager only (no local reproducibility). Consequences: vector sets carry the embedding identity and a mix across backends or models is refused (CC-13); ADR-4's single shared space still holds because both corpora use one chosen backend. ADR-15 · The web app is a user-run local process; query-time models are lazy, optional and configured by the user (answers Q-1)

Date: 2026-11-08. Context: new resumes and postings need steps 2, 5 and 6 at query time (ADR-2), which need the structuring LLM (Voyager or a local server, ADR-11, ADR-13) and the embedding model (ADR-14). Q-1 asked where these run. Voyager keys are personal and never held by agents (CC-10); Sol is a batch cluster; the RTX 5070 cannot hold a local LLM server and the embedding model together. Decision: the app is one process (webapp serve) on a team member's machine, binding to loopback, reading that user's .env through the CLI entry point only. It obtains clients from make_client and make_embedding_client, lazily, and reports in /api/health what it can do. Three query kinds degrade gracefully: a corpus document (needs neither model), a form (needs only the embedding model, or nothing for B1+), free text (needs both). Query-time labeling is lookup-only. Nothing is stored or logged from a query. A demo mode on built-in data needs nothing. Alternatives rejected: a hosted server with a shared team key (key exposure against CC-10, a retired model breaks it, no always-on host); structured-JSON-only input (loses the paste-a-resume flow; kept as the form); running the LLM relabeler per query (latency, cache management; revisit with data). Consequences: a live demo needs a configured laptop; the first form or text query pays the embedding model load; embedding calls are serialized; text queries send the user's text to the configured structuring service, which the UI states. Spec: web-app.

ADR-19 · The agent is a LangGraph state machine over a JSON action protocol, in an optional extra

Date: 2026-11-08. Context: ADR-10 and the proposal commit to a LangGraph agent with tools. LLMClient exposes only complete(system, user) -> str (ADR-11, ADR-13), with no tools or message lists, and the local backend's tool-call support varies by server. A four-node loop does not need a framework, so keeping LangGraph is the proposal's choice (confirmed by the user), not a technical necessity. Decision: the model replies with one JSON object per step, either a tool request or an answer, parsed and retried by complete_validated. LangGraph supplies only the state machine (StateGraph, conditional edges, a recursion limit); all node logic is plain Python in getwork.agent.turn, tested without LangGraph through a plain drive function. langgraph is an optional extra agent and is in the dev group, imported only inside build_graph; without it webapp serve --explainer agent exits 2 with an install hint and nothing else changes. Alternatives rejected: native function calling with langchain-openai (a second client stack the fake client cannot test); a hand-written loop with no dependency (cheaper and viable, but contradicts the proposal; the swap is one module, graph.py, plus the extra); making LangGraph a core dependency. Consequences: the agent runs on every backend and in tests with FakeLLMClient; the dependency footprint is langgraph plus langchain-core and a few helpers, paid only by users of the extra and developers. Spec: match-agent.

ADR-20 · Every agent claim passes a deterministic verifier; failures are plain-language errors; chat is stateless and whole-response

Date: 2026-11-08. Context: the proposal defines a hallucination as a skill named in an explanation that is in neither document's final skill set, and evaluates faithfulness by rating. An agent that may say anything can only be measured after the fact. The user decided that when the model fails the person should be told in plain words, not quietly given a different kind of explanation. Decision: the agent sees only structured fields (title, level, skills with clusters) and code-generated facts. It answers as claims that declare their documents, skills and fact ids; a verifier checks them against the facts and documents and sends violations back to the model (two retries). If the model call fails, the reply cannot be parsed, the time limit (60 s) or a budget (4 tool steps, 6 LLM calls) runs out, or verification still fails, the API returns HTTP 502 with the existing error envelope and the code assistant_failed, with a plain, non-technical message and a hint saying what to try, taken from a fixed table by failure reason; no explanation text is shown, the evidence chips on the card remain, and the rules explainer is used only when the server runs without the agent. Unverified answers are the same class as model failures because in both cases the assistant could not produce an answer fit to show. Chat is stateless (the client resends history, query view and result list), is not streamed (unverified text must never be shown), and logs no message text. Alternatives rejected: trusting the model and measuring afterwards (users would see hallucinations); an LLM verifier (circular); streaming (shows unverified text); server sessions (state and privacy cost for one local user); a silent rules fallback (the user rejected it; it also hides the failure from the evaluation); HTTP 200 with a message field (a second success shape that clients and the evaluation could mistake for an answer). Consequences: hallucinated skills cannot reach the UI through the vocabulary scan or declared skills, so the measured automatic rate on accepted answers is near zero by construction; the evaluation must therefore report the verifier's intervention rate (verify_retries), the error share by failure reason, and the judges' faithfulness ratings, not the automatic rate alone. A skill outside the taxonomy and alias vocabulary that is named only in prose is not detected by the scan. Spec: match-agent.

ADR-22 · Version and edition suffixes fold through a reviewed family list, applied when the alias table is built

Date: 2026-11-10. Context: the alias table (CC-2) merged only spelling variants, so Windows 7, Windows 10, Windows Server 2008 R2 and about 60 more Windows spellings stayed separate skills; the full-corpus k-means run produced a cluster that was mostly Windows versions, and version variants take slots in the top-1,000 selection. The vocabulary also holds numbers that are not versions (Cisco 3750, Catalyst 2950, ISO 27001, FIPS 199, 802.11, Route 53, S3, T1), which a regex cannot tell apart from versions. Decision: a reviewed CSV of product bases (version_families.csv, columns base,canonical,map_bare) defines which products fold; a fixed grammar (number, year, XP/NT-style release names, release suffix such as R2 or SP3, lists such as 7/8/10) decides what counts as a version after the base; the result is written into the table's entries for every corpus spelling, with curated rows still winning. The build also writes alias_version_report.json with folded groups and unfolded candidates so the list can be extended by review; the LLM proposer prompt (alias_v2) is a discovery aid and still only writes a draft. Alternatives rejected: a generic "strip trailing digits" rule (wrongly merges hardware models, standards and service names, as the evidence above shows); LLM-only grouping (top 600 skills only, non-deterministic, cannot be the guarantee); folding at lookup time inside AliasTable.canonical (would also fold unseen spellings, but changes the table file format and every consumer, and the version hash would need the rules; deferred, see the feature's Q-3). Consequences: an unseen spelling of a listed product (Windows 11 in a later resume) is not folded; a new product needs one CSV row; major versions merge (Python 2 and Python 3 are one skill; the alias_v1 sentence saying otherwise is removed); a new table version invalidates every later artifact, which must be rebuilt in the documented order (CC-12). Spec: alias-and-naming-v2. Deviation: P-16 (clarified).

ADR-23 · Cluster names are concept labels, checked in code, and a member-list name cannot build a taxonomy by default

Date: 2026-11-10. Context: the proposal's serialization example groups skills under names like Front-end and Cloud (CC-4), but all 30 names in the full-corpus run are the heuristic's first three members joined with / , because run_pipeline.sh passed --method heuristic; the LLM path had no rule against a reply that lists members, and duplicates were only flagged afterwards. The cluster name is part of every document's embedded text, so a member list repeats skills and adds no concept. Decision: (1) one deterministic definition of a member-list name (model.member_list_reason: strictly more than half of the name's parts, split on / | & + and and or on spaces, equal member skills); (2) LLM names must also not be generic words, longer than five words, one member skill, or a repeat of an earlier cluster's name, and each rejection goes back to the model as retry feedback through complete_validated; (3) clusters are named in id order with the names so far in the request; (4) the names file status gains member_list and taxonomy build exits 2 for such a name unless --allow-member-names is given; (5) run_pipeline.sh names with the LLM by default (NAME_METHOD). The prompt is name_v2, which asks for a concept label and gives good and bad examples. CC-14's name rules (check_name) are unchanged. Alternatives rejected: a prompt change alone (the heuristic and human edits would still ship member lists, and nothing would catch a drifting model); warning instead of refusing (that is how the current artifacts shipped heuristic names); a hand-written category dictionary (does not cover a new corpus); one LLM call naming all clusters (long reply, harder retry); rejecting single-member names at build (they are not lists, and a human may want one). Consequences: a default run needs a configured LLM for naming (user-run); clusters whose replies keep failing fall back to a heuristic name that must be edited before build; heterogeneous clusters still get weak names, which is a clustering issue; about a dozen existing build tests add the flag. Spec: alias-and-naming-v2.
