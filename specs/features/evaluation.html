Evaluation

The offline harness that compares B1+, B2 and Full: seeded query and posting-pool sampling, TREC-style pooling, two pluggable LLM judges, a blind-label hand-off for the two authors, metrics with bootstrap intervals, agreement statistics, taxonomy ARI and a report. Part 1 of 3 (the other two parts are named under Scope).

Goal

The project's research question is answered by comparing three systems, B1+, B2 and Full (Evaluation in the master, ADR-8, ADR-9, CC-6), on relevance labels in both directions. Nothing in the repo produces those labels or the numbers yet: retrieve run writes six top-10 files over the whole documents tables and stops. This feature builds the harness from those rankings to the final tables: it samples the dev, test and human-check queries and the capped posting pool, ranks inside that pool, pools and blinds the pairs, runs two independent LLM judges behind an interface, combines their labels, computes P@5, P@10, MRR and nDCG@10 with bootstrap confidence intervals, system gaps with a paired randomization test, Cohen's kappa and Kendall's tau between judges and the two authors, the taxonomy ARI, and writes one report.

Every real model call in this harness (the judge runs) is a user-run command (CC-10). Agents build and test everything against fake judges and tiny offline fixtures. Outputs go to a new directory the user chooses (default eval_out/); nothing under data/ or artifacts_trial/ is written.

Current state this spec starts from (branch dev, HEAD 578e2f3): src/getwork/retrieval is built (retrieve run, retrieve show; b1plus.py already has grid_search_weights(objective, step)); the documents tables and vectors exist in artifacts_trial/v5 (4,258 resumes, 1,000 postings; the user is rebuilding into v6 with 8,423 postings). The empty evaluations/ directory of the earlier layout proposal is not used. There is no evaluation package, no evaluate script and no judge code. Artifact sizes are parameters throughout; no number in this spec's tests depends on the v5 or v6 sizes.

Scope

Split into three features, recommended order

The request (pooling, two judges, a blind human-labeling UI, metrics, agreement, ARI, substitution test, explanation ratings and hallucination rate) is about 45 tasks in three different concerns. This spec is part 1; parts 2 and 3 get their own specs once part 1 is built, because they depend on its file contracts (CC-20).

  1. evaluation (this spec, build first): everything that runs offline or behind the judge interface: sampling, capped pool, pooling and blind pair files, rubric and judges, label combination, metrics and statistics, agreement (judges, authors), B1+ weight tuning on the dev set, taxonomy ARI, report, runbook. It reads the authors' labels from a file format defined here.
  2. labeling-ui (second; row already in the feature index, status proposed): the blind pair-labeling page on the web-app server for the two authors. It reads pairs_blind_human.jsonl and writes human/<author>.jsonl (CC-20). It can be built in parallel with part 1 after T-6 and T-7 exist, and it is needed before the human check (week 6).
  3. evaluation-probes (third; new row, proposed): the controlled substitution test (needs the embedding client and the relabel code), the explanation generation with the chat agent, the judges' 1 to 5 explanation ratings, the automatic hallucination rate (grounding.ungrounded_skills) and the 10 hand-reviewed explanations, plus its report section. It reuses this spec's Judge seam, JudgeInfo, check_independence, run directory and the reserved probes/ folder.

In scope (this spec)

  • A new package src/getwork/evaluation/ with the console script evaluate and these commands: sample, pool, judge, labels, freeze-rubric, tune (plan, pick), metrics, agreement, ari, report.
  • Seeded sampling of the posting pool (cap 5,000, a parameter) and of the dev, test and human-check queries for both directions; ranking of B1+, B2 and Full inside the pool with the retrieval code.
  • The pluggable judge interface, the rubric file and its frozen hash, an LLM judge on LLMClient, a fake judge, independence checks, the lower-label rule with the code-enforced seniority cap, resumable and concurrent judge runs.
  • Metrics, bootstrap intervals, paired randomization test, gaps, Cohen's kappa, Kendall's tau, the judge-versus-author agreement and the fallback decision of ADR-9, taxonomy ARI against occupation labels, the B1+ dev-set tuning loop, the markdown report.
  • A runbook (src/getwork/evaluation/README.md), scripts/run_evaluation.sh, a short section in docs/running-end-to-end.md, and a user-run checklist for the real judge runs.

Out of scope

  • Parts 2 and 3 above: the labeling UI, the substitution test, explanation generation, ratings, hallucination rate and hand review. This spec only reserves probes/ and defines the human-label file the UI will write.
  • Any change under data/ or artifacts_trial/, to the retrieval, docembed, relabel, taxonomy, webapp or agent packages, to /api, or to the web UI. The one existing test file edited is src/tests/common/test_pipeline_offline.py (one word added to PREFIXES).
  • Changing the default judges (Q-5 is answered: gemma4-31b-it, family google, and llama4-maverick-17b, family meta; they are constants in defaults.py and options can override them), editing the rubric wording after the dev stage (the user does that), and the report's prose in the final paper.
  • Any real Voyager, LLM or embedding call by an agent, and any read of .env (CC-10). Every test uses FakeJudge, FakeLLMClient or FakeEmbeddingClient and the offline fixture.

Decisions

IdDecisionWhy
D-1One package, one console script, one command per stage, state in files. getwork.evaluation, script evaluate. Every command reads the previous stage's files from --out-dir and writes its own with the atomic writers in getwork.fileio. Commands that make model calls are resumable (a re-run only does the missing work). (ADR-36)The protocol has manual steps (rubric review, tuning, human labeling) between machine steps, so one evaluate all cannot exist. File-based stages match how taxonomy and retrieve work.
D-2Output directory. --out-dir, default eval_out. check_out_dir refuses (exit 2, nothing created) a directory equal to or inside data, the resolved artifacts root, --artifacts-dir, --processed-dir or the three trial defaults of getwork.paths. Inputs are only read.Hard constraint: agents and the harness never write under data/ or artifacts_trial/. A refusal is testable; a convention is not.
D-3The evaluated ranking is recomputed inside the capped pool. The pool is a seeded sample of at most pool_cap (default 5,000) posting ids from the postings documents table. For resume_to_posting the candidates are the pool; for posting_to_resume they are all resumes of the documents table. Rankings come from retrieval.run.make_plan and run.rank on inputs restricted to the sampled queries and candidates; the six stored topk_*.parquet files are not read. (ADR-37)The stored files rank against every posting. With 8,423 postings the cap of 5,000 would otherwise not hold, and filtering stored top-10s to the pool leaves fewer than 10 results. Reusing the retrieval code keeps scoring identical (AC-11 proves it).
D-4Query sampling. Resumes: only resumes with a first occupation label; equal allocation across labels (quota n // L, the remainder one each to the first labels in sorted order, quotas capped by label size with the shortfall handed round-robin to labels that have spare). Postings: uniform from the pool. Order of draws: dev, then test from the rest, then human from test. All draws use random.Random(f"{seed}/{purpose}") over sorted ids, so they do not depend on dict order or PYTHONHASHSEED."Stratified by first occupation label" is in the master; equal allocation is the reading of "balanced" (assumption A-3). Independent seeded draws make every set reproducible and stable when another size changes.
D-5A pair is (resume_id, posting_id), direction-agnostic. Its id is "p-" + sha256(f"{seed}:{resume_id}:{posting_id}").hexdigest()[:12]. A pair retrieved in both directions, or by several systems, is judged and labeled once. Judges and humans always see the resume in the resume role and the posting in the posting role.Halves the judge calls and makes labels comparable across directions. A stable hashed id lets stages, the labeling UI and the judges share ids without sharing order.
D-6Blind files carry only {pair_id, resume_id, posting_id}. The union of the three systems' top-10 for the stage's queries is shuffled by a seeded RNG. System ids, ranks, scores and directions live only in pool_rankings_<stage>.parquet; pairs_<stage>.parquet keeps the directions but never systems. Judge prompts and the UI never see them (CC-8).CC-8. A reviewer can check the blind files mechanically (AC-13, AC-26).
D-7Judges behind a Judge protocol. LLMJudge (on LLMClient, so Voyager and local backends work) and FakeJudge (tests). A judge replies with one JSON object {"label": 0|1|2, "seniority_mismatch": bool, "rationale": string}; the request carries it as a strict response_schema (judges.VERDICT_SCHEMA) and the reply is validated by parse_verdict either way (D-16). The code, not the model, applies the cap: effective_label = min(label, 1) when seniority_mismatch is true (CC-7). The final label of a pair is the lower of the two judges' effective labels. A judge sees the cleaned text of the resume and of the posting (text_clean from the processed parquet), truncated at --max-chars per document with a recorded flag; never the structured records. (ADR-38)ADR-9 and the master: judges read raw text so structuring errors do not leak into the labels. Enforcing the cap in code makes CC-7 testable and independent of how well the model follows the rubric.
D-8Judge independence is checked in code. check_independence requires exactly two judges with distinct ids and distinct family labels (casefolded) and refuses a judge whose model equals any model used by the pipeline: the model values in canonical/<source>/<source>_canonical.jsonl, every non-null relabel_model in the documents summaries, and the models in defaults.DEFAULT_ALSO_USED_MODELS (qwen38-27b, the structuring, relabel and chat-agent model) plus any --also-used-model the user passes (a different agent model must be passed this way). The check runs on the default judges too. Families are declared (defaults google and meta, option --judge-families); the harness cannot infer them.ADR-9 says "different model families, neither used in the pipeline or agent". A refusal before spending calls is cheaper than a retraction. qwen38-27b is a default entry rather than a printed warning because a forgotten flag would then silently let the agent's model judge, whereas an always-checked default cannot be forgotten; the cost is that a user who moves the agent to another model must still pass it (the summary lists every model checked).
D-9The rubric is a versioned file and is frozen by hash. prompts/judge_v1.md ships with the package; --rubric-file overrides it. freeze-rubric records its sha256 (12 hex) in rubric_frozen.json. judge --stage test refuses unless the file exists and the current rubric hash equals it. Judge rows carry the rubric hash; label building ignores rows with another hash.ADR-9: the test pairs must never shape the rubric. The one allowed revision (fallback) is a deliberate delete-and-refreeze by the user; old rows stay on disk but are ignored.
D-10Metric definitions. Per query and system over the top 10: P@5 and P@10 = (number of label-2 documents in the top K) / K (K is the denominator even when fewer than K results exist); MRR = 1/rank of the first label-2 document in the top 10, else 0; nDCG@10 with linear gain label, discount 1/log2(rank+1), ideal DCG from the labels of every pair pooled for that query (union of the three systems' top-10), 0.0 when the ideal DCG is 0. Per direction, the mean over queries. (assumption A-2)The master fixes "only label 2 counts" and "nDCG@10" but not the gain or the ideal list. Pooled ideal is the TREC convention; linear gain keeps the label scale readable.
D-11Statistics. Per-query values are the unit. 95% percentile bootstrap over queries (default 10,000 resamples, seeded) for each mean and for each system gap (paired: the interval of the per-query differences). Gaps: B2-B1+, Full-B2, Full-B1+. p-value: two-sided paired sign-flip randomization test on the per-query differences (default 10,000 flips, seeded), p = (1 + #{|mean_flip| >= |mean_obs|}) / (1 + n_flip), and 1.0 when every difference is 0. No multiplicity correction (stated in the report). Cohen's kappa unweighted is the headline agreement (threshold 0.6); quadratic-weighted kappa and percent agreement are reported beside it. Kendall's tau-b between system orders. (ADR-39)Master: "95% bootstrap CIs; paired randomization test on per-query scores, judge labels". With three systems tau takes values 1, 1/3, -1/3, -1 only, so the gaps are always reported with it.
D-12Human labels contract. One file per author, human/<author>.jsonl, rows {"pair_id", "author", "label", "labeled_at"}; author is a slug [a-z0-9_-]{1,20}, not judge; a later row for the same pair replaces an earlier one. The blind file the authors label is pairs_blind_human.jsonl. The harness validates ids and labels on read (CC-20).Fixes the interface between parts 1 and 2, so the UI can be built against it before the metrics exist.
D-13Agreement and the fallback rule. Judge-vs-judge kappa is computed on the dev and the test pairs. For the human check: author-vs-author kappa; each judge's effective label and the final label against each author; human_judge_kappa = mean of the two judges' unweighted kappas against each author. fallback_decision: judges_reliable when human_judge_kappa >= 0.6; else revise_once when author_kappa >= 0.6; else subjective; undetermined when either kappa is undefined. --half first|second restricts the human pairs to the diagnostic half or the untouched half (A-8).Master Evaluation, "Fallback when judges disagree with humans", written as a pure function so the rule is tested, not remembered.
D-14B1+ tuning on the dev set in two offline commands. tune plan lists every pair needed to score all weight candidates (default step 0.1, 66 candidates) and writes them as the tune stage; the user judges that stage with the normal judge command; tune pick then maximizes the mean nDCG@10 over the dev queries of both directions (candidates enumerated with b1plus.grid_search_weights; the first candidate with the best value wins ties, the same rule) and writes tune/b1plus_weights.json in the format b1plus.load_weights reads. It refuses to run when any needed pair has no label. pick recomputes the candidate rankings, so it must be given the same --step and --k as plan: plan records neither in run.json and nothing checks it; with different values some top-10 pairs were never judged and the command fails with the missing-labels error (exit 2), whose hint names both evaluate judge --stage dev and evaluate judge --stage tune. pick records its own step in run.json["tune"].A weight candidate's top-10 contains pairs the default weights never retrieved, so tuning needs new labels. Making that explicit and bounded (plan prints the count) avoids a hidden, unbounded loop of judge calls.
D-15Exit codes and error handling follow the existing CLIs. 0 ok; 1 the judge run finished but some pairs failed (re-run retries them); 2 usage, config or input error (including StaleRunError and missing labels), checked before any output or model call, order: arguments, client and config, then inputs (CC-10; --dry-run skips client construction); 3 fatal LLM error. Every command prints one JSON summary to stdout.Matches taxonomy, retrieve and structurer.
D-16Default judges and how the request is shaped (answers Q-5). All of this lives in one module, defaults.py (I-15). Judge judge-a = gemma4-31b-it, family google; judge judge-b = llama4-maverick-17b, family meta; backend Voyager. evaluate judge uses them when --judge-models and --judge-families are absent; the two options must be given together (one without the other is exit 2). Both models were checked by the user in Voyager's /v1/models: context 131,072 tokens, supports_response_schema true. Reasoning: --reasoning-effort defaults to auto, which sends none to gemma4-31b-it and sends nothing to llama4-maverick-17b (it has no reasoning control, so LLMRequest.reasoning_effort is None, which VoyagerClient omits from the call); an unknown model also gets nothing under auto; an explicit value (none|low|medium|high) applies to both judges and omit sends nothing to both. Schema: LLMJudge first sends response_schema = VERDICT_SCHEMA; if the provider answers a permanent error (HTTP 400, 413 or 422 style, PermanentLLMError) the same pair is retried once without a schema, and only when that plain call succeeds does the judge stop sending the schema for the rest of the run (a document that is too long fails both calls and does not switch it off); either way the reply goes through parse_verdict and the 3-attempt validate-and-regenerate loop. The run summary reports schema_fallback per judge.The user chose and checked these two models. Different vendors (Google, Meta) from the pipeline's Qwen satisfy ADR-9. Sending a reasoning control to a model that lacks it can be rejected by the provider, so the table is explicit and the unknown case sends nothing. A strict schema makes malformed JSON rare but a provider can still reject it, so the plain-JSON path is the safety net the structurer's --no-response-schema also needed.

Run order (what the user does)

  1. Sample (offline). evaluate sample writes the pool, the dev, test and human query sets and the run manifest.
  2. Pool the dev stage (offline). evaluate pool --stage dev ranks B1+, B2, Full inside the pool and writes the blind dev pairs.
  3. Judge the dev stage (user-run, real calls). evaluate judge --preflight (both default judge ids found, schema support shown), then evaluate judge --stage dev (first with --dry-run, then --limit 5, then in full); read rationales on 20 to 30 pairs; edit the rubric; repeat until evaluate agreement --scope judges --stage dev shows kappa at least 0.6.
  4. Tune B1+ (offline plus user-run judging). evaluate tune plan, evaluate judge --stage tune, evaluate tune pick.
  5. Freeze the rubric. evaluate freeze-rubric.
  6. Pool and judge the test stage. evaluate pool --stage test --weights-file eval_out/tune/b1plus_weights.json, then evaluate judge --stage test (user-run, real calls). This writes pairs_blind_human.jsonl for the authors.
  7. Human check. The two authors label pairs_blind_human.jsonl in the labeling UI (part 2); files appear under human/.
  8. Numbers. evaluate metrics (judge@test, judge@human, each author@human), evaluate agreement --scope human, evaluate ari, evaluate report.

Edge cases & risks

  • Pool larger than the cap. With 8,423 postings in v6 the cap of 5,000 is active; with 1,000 in v5 it is not and the pool is everything. The report prints the cap (run.json params); the pool size is in sets.json as n_pool and the report does not print it. Dev, test and human posting queries are drawn from the pool, so every posting query is also a candidate for resume queries (a pool member can be both).
  • Unlabeled resumes. 745 of the 28,842 cleaned resumes (about 2.6%) have no occupation label (deviations "Implied or undocumented" and Data facts). They are never sampled as resume queries and are excluded from ARI; they remain candidates in the posting-to-resume direction. If fewer labeled resumes exist than dev plus test, sample exits 2.
  • Labels with fewer resumes than their quota. The shortfall is redistributed (D-4); with 9 labels in the corpus (the processed data has 9 distinct first_label values, not 10) a quota of 11 or 12 per label results. The report prints the label list so "k=10" versus 9 labels is visible.
  • Small pools or tiny corpora. k_effective can be below 10; P@10 still divides by 10 (D-10) and the test tree's pools are smaller than 10 in some tests, which is intended.
  • Pairs seen in both directions or by several systems are judged once; a pair retrieved only by one system still counts in every system's ideal DCG for its query (pool union), the standard pooling bias that favors the systems that contributed; the report's caveat says so only through "pooled labels".
  • Re-sampling. evaluate sample --force replaces sets.json, so the pair, judge-row and label files of the old sample no longer describe the new queries. They are not deleted; the README tells the user to start a new --out-dir instead. Stale-stamp checks (D-15) catch a changed corpus or taxonomy, not a changed sample.
  • Tuning arguments. tune plan and tune pick must use the same --step and --k (D-14); nothing records or checks it, and a mismatch shows up as the missing-labels error.
  • Judge failures. A failed pair has no label and is absent from labels_judge.parquet; metrics then exits 2 with the missing count (no silent zeros). The user re-runs judge, which retries only the failed or missing pairs. --allow-missing exists for an explicit, recorded "missing counts as not relevant" run.
  • Torn writes and crashes. The judge file is append-only with one flushed line per pair; a crash can leave a partial last line, which the reader ignores. All other outputs use the atomic writers.
  • Rubric changes after freeze. Judging test with a different rubric hash is refused (exit 2). Old rows with another hash stay in the file but are ignored; deleting a judge file by hand is also safe (resumable).
  • Judge model or family changed mid-run. Refused by comparing with run.json["judges"]; the user starts a new out-dir instead, so labels from two different judge pairs are never mixed.
  • Long documents. Resumes have a 75th percentile of about 9,000 characters and a maximum of about 88,000; postings top out near 21,000. --max-chars 20000 cuts few documents; the truncated count is in every summary and in the report. A cut resume may lose later experience, which is a known bias toward lower labels.
  • Hash collisions of pair ids (48 bits) are astronomically unlikely at a few thousand pairs and are detected, not ignored (AC-12).
  • nDCG when no relevant document exists in a query's pool. nDCG is 0 for all systems for that query; the count is reported as n_no_relevant. These queries still dilute the means equally for the three systems.
  • Few queries. The human set has 10 + 10 queries, so its intervals are wide and the smallest possible p of the randomization test is 1/(n_perm+1) but with 10 queries the number of distinct sign patterns is 1,024; the Monte Carlo p is then only approximate near 0.001. Report the human-check gaps descriptively; the primary inference is on judge@test.
  • Multiple comparisons. Three gaps times four metrics times two directions are tested with no correction (D-11); the report says so.
  • Tuning overfits 20 queries. The dev set is tiny. The grid is coarse (step 0.1) on purpose and the chosen weights, the objective and the full tune_results.csv are in the report inputs; if the objective surface is flat the first candidate (all weight on skills) wins ties, which is a documented bias (ADR-8 weights default to 0.7/0.15/0.15, not 1/0/0). The user may pass --weights by hand to pool instead.
  • B2 text order leaks taxonomy information. Open question Q-10 in the master: with the default b2_order = "grouped" B2's text lists skills in cluster order, so part of the taxonomy effect can appear in B2. The report prints the stamp and a caveat; the user may rebuild documents with --b2-order record for a cleaner ablation.
  • Judge independence is declarative. Families are what the user types or the defaults say (google, meta); the harness cannot verify them. The model-name check only catches identical names (a fine-tune or alias of a pipeline model passes); qwen38-27b is always in the checked list. If the chat agent later runs on another model, the user must pass it with --also-used-model, and the summary's checked_against shows what was checked.
  • Provider and model quirks. llama4-maverick-17b has no reasoning control, so nothing is sent (D-16). If either judge's provider rejects the strict schema, the judge falls back to plain JSON (reported as schema_fallback); a prompt that exceeds the 131,072-token context is a permanent error for that pair only (a failed row, retried on the next run). A model id that disappears from /v1/models (Voyager retires models, ADR-11) is a fatal error (exit 3); --preflight catches it before spending calls.
  • Judge cost. About 2 x (pairs of dev + test + tune). With 200 test queries and about 20 pooled pairs per query, about 4,000 test pairs, so about 8,000 test calls, plus dev (about 400 calls) and tuning (66 candidates x 20 queries can add several hundred to a few thousand new pairs; use tune plan first and a coarser --step 0.5 if the count is too large).
  • Existing retrieval README. It says retrieve run saves "the ranked lists that evaluation pools and judges". This spec does not use those files (ADR-37); the sentence is left as is and the evaluation README explains why.
  • uv.lock. No new dependency is added (scikit-learn, scipy, numpy, pyarrow are present), so the lock stays valid; only the new script entry is added to pyproject.toml.
