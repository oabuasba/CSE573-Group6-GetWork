Parallel cluster naming with progress lines

Run the per-cluster naming calls concurrently, fix duplicate names afterwards in cluster-id order, and print one stderr line per cluster.

Status: draftUpdated: 2026-11-10Pipeline step: 4 (taxonomy name)Master: architecture.html
naming-parallel

Goal

taxonomy name --method llm (built in alias-and-naming-v2, decision N-3) asks the model about one cluster at a time so that each request can list the names already used. With the full-corpus selection possibly at 71 clusters (hdbscan-01) that is 71 sequential calls with no sign of life. This feature adds --workers N so the calls run concurrently without the used-names list, then checks the results in cluster-id order and re-asks sequentially, with the used-names list and the existing retry feedback, only for the clusters whose draft repeats an earlier accepted name. The outcome does not depend on which call finishes first. It also prints one stderr line per cluster as it is accepted or falls back, and keeps the single JSON summary line on stdout. workers=1 stays the current sequential behavior. Spec decisions are recorded in ADR-24.

Scope

In scope

  • naming.name_clusters: workers and log keyword parameters, the two-phase algorithm for workers >= 2, per-cluster call statistics merged at the end, progress message builders.
  • taxonomy name --workers N and the stderr progress lines (redacted); scripts/run_pipeline.sh passes NAME_WORKERS (default 4).
  • Taxonomy README text and a docs test.

Out of scope

  • Any change to the name rules (check_concept_name, member_list_reason), the prompt (name_v2), the names file columns, the build gate, or the stdout JSON summary keys.
  • Parallelism for other steps, and moving structure/pool.py to a neutral module (see assumption A-2).
  • A --quiet flag (assumption A-3). Real LLM or Voyager runs: user-run only; tests use FakeLLMClient (CC-10). docs/deviations.md is untouched.
  • The done tasks T-1 to T-10 of alias-and-naming-v2 stay as built; this feature only adds tasks.

Design

Depends on ADR-13 (client factory, retry, validated loop), ADR-23 (concept-label names), CC-10, CC-14, and adds ADR-24. The structurer's existing worker pattern is reused as is: getwork.structure.pool.run_pool(items, fn, workers, stop, abort) runs fn over the items on daemon threads and yields (item, result) in arrival order, an exception from fn arrives as the result, and the consumer sets abort and abandons the generator on a fatal error (see structure/runner.py, _consume). One shared Throttle serves all workers so a 429 pauses everyone. The structurer prints progress to stderr through a log callable that the CLI wraps with redact_secrets; this feature does the same.

Decisions

IdDecisionRationale
P-1workers == 1 (the default) runs today's loop unchanged: ids ascending, each request carries USED NAMES (all names accepted so far), validation includes the duplicate rule. workers >= 2 runs the parallel algorithm P-2. workers < 1 raises ValueError.Compatibility. The default stays 1 as the user suggested (the structurer's default is 4, or 2 for the local backend); the pipeline script passes 4.
P-2Parallel algorithm. Draft phase (concurrent, one task per cluster): one complete_validated call per cluster with used empty, so the request text is exactly build_name_message(shown, ()). The validation is parse_name(text, shown, ()), which includes the member-list, generic, word-count and single-member rules, so a member-list reply is retried with the existing feedback inside the worker, concurrently. A draft ends as a name, or as a failure of type ValidationExhausted, RetriesExhausted or PermanentLLMError; FatalLLMError aborts the run (P-5). Resolve phase (the consuming thread, ids ascending, started as soon as the next id's draft has arrived): keep the list accepted of accepted names. A draft name whose casefold is not in accepted is accepted as is. A draft name that repeats an accepted one is discarded and the cluster is re-asked once through complete_validated with used = tuple(accepted) (same request and validation as workers == 1, full retry budget); accepted if it passes, else a fallback. A failed draft is a fallback (no second chance: repeating a transport failure or three rejected replies is not useful). The lower cluster id always keeps a contested name.Draft requests do not depend on each other, so they can overlap; the only cross-cluster rule is uniqueness, and resolving it in id order makes the result independent of finish order. Resolve work (rare re-asks) runs while the workers keep drafting.
P-3Refinement of the user's wording: member-list replies are retried with feedback inside the concurrent draft phase (the existing three attempts), not in the sequential phase, because the concept rules do not depend on other clusters. Only duplicates, which do depend on other clusters, are re-asked sequentially. A cluster whose draft was a member list on every attempt falls back, as today.Same final behavior as "re-ask member lists sequentially" with fewer sequential calls. Alternative: make the draft phase single-attempt and re-ask every rejection sequentially; slower on a bad run, not taken.
P-4Determinism. For a fixed model, for every workers >= 2 the names, the fallback list and the sequence of progress lines are the same whatever the number of workers and the order in which calls finish, because each draft depends only on its cluster's own replies and the resolve phase follows id order. workers == 1 and workers >= 2 may differ, because the model sees the used-names list from the first request only when workers == 1; this is stated in the runbook.The user asked for results independent of finish order; making workers == 1 identical to workers >= 2 would change today's requests.
P-5Errors. FatalLLMError from a worker or from a re-ask: set abort, stop consuming, re-raise it unchanged (the CLI redacts it and exits 3, as today). Any other unexpected exception from a worker is re-raised the same way. RetriesExhausted and PermanentLLMError fail one cluster only. The pool is always abandoned with abort set (finally), so no new cluster starts after an error.Matches the structurer pool and _consume.
P-6Call statistics: each cluster has its own CallStats (the counters are not thread-safe); NameResult.stats is their field-wise sum, in every mode. "Attempts" in progress lines means the model calls made for that cluster, drafts and re-asks together (CallStats.calls).Same pattern as the structurer's per-record stats.
P-7Progress. name_clusters(..., log=callable) calls log once per cluster, in id order, when its outcome is final: named {done}/{total}: cluster {id} -> "{name}" (attempts {n}) or fallback {done}/{total}: cluster {id} ({reason}, attempts {n}) where done counts finished clusters including this one, name is json.dumps(name) of the accepted name, and reason comes from a fixed table (no exception text, no raw reply). The CLI sends the lines to stderr through redact_secrets; the stdout summary is unchanged. No lines for --method heuristic (instant, nothing to report).The user's example format. Fixed reasons keep model text and error bodies out of logs.
P-8No --quiet. None of the CLIs has one: the structurer logs to stderr unconditionally and taxonomy embed prints chunk progress to stderr unconditionally. Progress goes to stderr only, so 2>/dev/null silences it and stdout stays one JSON line.Consistency over a new flag; the flag is cheap to add later.

Data flow

Same inputs and outputs as before (selection state in, cluster_names.csv and one stdout JSON line out). New: stderr gets one line per cluster for --method llm. Draft requests are sent in id order across the workers; the resolve phase consumes drafts as they arrive and releases them in id order.

Open questions

Assumptions

A-1. Default --workers is 1 (as suggested) and run_pipeline.sh defaults NAME_WORKERS to 4. Alternative: default 4 in the CLI like the structurer (2 for the local backend); not taken to keep today's behavior for anyone calling the command directly.

A-2. The pool is imported from getwork.structure.pool unchanged. Decision A-8 of alias-table prefers neutral modules for shared plumbing, but moving the pool would touch the finished structurer (imports, tests); a later refactor can move it to getwork.llm. Thread names stay structure-worker-N.

A-3. No --quiet (no other CLI has one). Alternative: add it to taxonomy name only; a flag that exists in one command is less consistent than none.

A-4. Member-list replies are retried inside the concurrent draft phase rather than re-asked sequentially (P-3); only duplicates are re-asked sequentially. Same final outcome as the user's wording with fewer sequential calls.

A-5. "Result independent of worker count" is guaranteed among worker counts of 2 or more; --workers 1 keeps today's used-names-in-every-request behavior and may name differently (P-4).

A-6. "Attempts" in progress lines is the number of model calls made for the cluster, transient retries included.

A-7. Progress lines for the heuristic method are not printed (instant).
