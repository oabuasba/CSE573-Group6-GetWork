Web app

A local FastAPI service and a React UI, themed from the public ASU brand guide, where a candidate pastes a resume to get ranked postings, or a recruiter pastes a posting to get ranked candidates, each with an evidence-based explanation.

web-app

Goal

The pipeline built so far ends in artifacts on disk: canonical records, a taxonomy, document texts and vectors, and precomputed top-k rankings. Nobody can use them yet. This feature puts a user interface on them. A candidate gives a resume (pasted text, a short form, or an example from the corpus) and gets the top-k postings; a recruiter gives a posting and gets the top-k candidates. A new text goes through the same steps as the corpus (structure, canonicalize with the alias table, label with the taxonomy, serialize, embed) and is ranked against the stored vectors of the other side with the same exact cosine top-k as the offline run (ADR-2, ADR-7). Every match carries explanation evidence computed from the two final skill sets: shared skills, related skills grouped under their cluster (the React and Vue case), and skills the posting asks for that the resume does not show. A narrative is produced by an Explainer behind a protocol; this feature ships a deterministic, faithful-by-construction explainer, and match-agent will plug its LangGraph agent into the same seam (ADR-16). The UI follows the ASU brand guide using plain CSS custom properties and Arial, with no ASU logos and no code taken from any ASU repository (ADR-18). It runs on one user's machine with their own keys (ADR-15) and can run on built-in demo data with no artifacts, no key and no GPU.

Scope

In scope

  • Backend package getwork.webapp: API models, an Engine protocol with a DemoEngine (built-in data) and an ArtifactEngine (real artifacts under artifacts_trial/ or artifacts/, either a complete run folder or a folder of vN runs, resolved by resolve_artifacts_root), the evidence builder and TemplateExplainer, the FastAPI app, and the webapp command (serve, check).
  • Three ways to supply a query: a corpus document by id (the "example" flow), a short structured form, and free text structured by the LLM at query time (ADR-15).
  • Frontend src/web: React 18 + Vite, JavaScript, three screens (Find jobs, Find candidates, About), hand-written CSS themed with the ASU brand-guide tokens (Theme tokens section), accessibility to WCAG 2.1 AA as far as it can be tested offline.
  • Error, empty, loading and capability-unavailable states; local run instructions; offline tests on both sides (pytest with FakeLLMClient and FakeEmbeddingClient; Vitest with injected fetch).
  • Guardrail tests: no ASU GitHub reference or dependency, no ASU logo or image assets, no external network loads from the page.

Out of scope

  • The LangGraph explanation agent, its tools, and chat follow-ups: match-agent (ADR-10). This feature only defines the seam and ships the deterministic explainer. The master's old index row said "chat"; that is moved there.
  • Blind pair labeling (CC-8, ADR-9): a new row labeling-ui needs eval-sampling-pooling first. It will reuse this feature's server, theme and API conventions.
  • Accounts, login, saved searches, a database, query logging, multi-user hosting, deployment, HTTPS. The server binds to loopback and keeps no state.
  • PDF or DOCX parsing. Text is pasted, or a .txt/.md file is read in the browser into the text box.
  • Rebuilding the taxonomy or any artifact from the UI; relabeling unseen skills with the LLM at query time (lookup-only, see assumptions); tuning B1+ weights.
  • Dark mode (the brand guide gives no dark palette), internationalization, mobile-app packaging.
  • ASU logos, the sun devil, Sparky, and any official ASU web header or footer component (ADR-18).

Design

One stateless JSON API in front of an Engine that hides where documents and vectors come from. Cites ADR-2, ADR-4, ADR-5, ADR-7, ADR-8, ADR-11, ADR-12, ADR-13, ADR-14, and adds ADR-15 (query-time hosting, answers Q-1), ADR-16 (explainer seam), ADR-17 (stack) and ADR-18 (ASU theming). Contracts used: CC-1, CC-2, CC-4, CC-5, CC-6, CC-10, CC-11, CC-12, CC-13, CC-14, CC-15, CC-16; adds CC-18 (web API and Explainer).

Every non-2xx response is {"error": {"code", "message", "hint", "field"}} (ErrorEnvelope), including validation errors and unknown /api/* paths (404 not_found). An unexpected exception is 500 internal with the fixed message "Something went wrong on the server" and no traceback or exception text; the traceback goes to the server log with configured secrets redacted. Neither request bodies nor query text are logged. The app adds no CORS middleware.

# src/getwork/webapp/explain.py
from typing import Protocol
def build_evidence(direction: Direction, query: DocumentView, match: DocumentView) -> Evidence:
    """resume, posting = (query, match) for resume_to_posting, else (match, query). Skills are compared by
    normalize_key. Key order is the order of first appearance.
    shared: posting skills whose key is among the resume's keys, in posting order, SharedSkill(skill=posting
      spelling, cluster=posting-side cluster).
    related: for posting skills not shared and whose cluster is not OTHER, group by cluster in order of the first
      posting skill of each cluster; the group's resume_skills are the resume skills not shared whose cluster equals
      that cluster; a group is emitted only if both lists are non-empty.
    gaps: posting skills not shared and not in any emitted related group, GapSkill in posting order.
    level: LevelComparison(resume=resume.level, posting=posting.level, relation) with relation "unknown" when either
      level_rank is None, else "same" (equal rank), "adjacent" (difference 1), "different" (2 or more).
    title_overlap: sorted(title_tokens(resume.title) & title_tokens(posting.title)).
    The result is the same for both directions when the same two documents are given swapped."""
class Explainer(Protocol):
    @property
    def info(self) -> ExplainerInfo: ...
    def explain(self, direction: Direction, query: DocumentView, match: DocumentView) -> Explanation: ...
class TemplateExplainer:
    info: ExplainerInfo                      # ExplainerInfo(kind="template", model=None)
    def explain(self, direction: Direction, query: DocumentView, match: DocumentView) -> Explanation:
        """evidence = build_evidence(...). summary = f"{n(S, 'shared skill')}, {n(R, 'related group')}, {n(G, 'gap')}."
        where n(c, w) is f"{c} {w}" for c == 1 and f"{c} {w}s" otherwise, S, R, G the lengths of shared, related, gaps.
        bullets, in this order, each only when applicable:
        1 "Shared skills: A, B, C." (at most 8 names, then " and N more" before the period);
        2 per related group: f"Related through {cluster}: the resume lists {resume skills joined by ', '}, the
          posting asks for {posting skills joined by ', '}.";
        3 "The posting asks for skills the resume does not show: X, Y." (gaps, at most 8 names, same overflow rule);
        4 level by relation: same -> f"Experience level is the same ({level})."; adjacent -> f"Experience levels are
          adjacent (resume: {r}, posting: {p})."; different -> f"Experience levels differ (resume: {r}, posting: {p}).";
          unknown -> omitted;
        5 "Shared title words: a, b." when title_overlap is non-empty;
        6 if bullets is empty: "No shared or related skills were found; this match comes from overall document
          similarity." Every skill name that appears comes from the two documents' skill lists."""

Query-time rules (ArtifactEngine)

  1. Side. resume_to_posting queries are resumes (source resumes); posting_to_resume queries are postings (postings). An id belongs to a side by the documents table that holds it (resume ids are r-N, real posting ids p-N, demo posting ids j-N).
  2. Form. Skills are trimmed; blanks dropped; the record is a dict with exactly schema.RECORD_KEYS (id "q-1", the side's source, experience and education empty, model "form", prompt_version "form_v1", schema_version SCHEMA_VERSION, backend "form"). Title and skills both empty: empty_query. Then canonicalize_record.
  3. Text. Blank after strip: empty_query; longer than max_query_chars: text_too_long (message contains the limit). Otherwise structure_one(client, cfg, Throttle(), SourceDoc("q-1", source, title, text), secrets) once; Outcome.failure becomes structuring_failed with the failure's redacted message; FatalLLMError becomes structuring_failed with the generic message "The model service rejected the request" and the same status. The text is never stored or logged.
  4. Label. split_known against the taxonomy; each unseen skill becomes SkillAssignment(skill, OTHER, "default") (lookup-only, assumption A-2); incomplete_reason from known_fraction and the source's p10; build_relabel_record(record, assignments, [], incomplete, False, tax, None).
  5. Document. build_document(relabeled, listed_level, tax, bands, b2_order) where bands and b2_order come from that side's documents summary (level_bands, b2_order) so the text is serialized exactly like the corpus; listed_level is the form's level for postings and None otherwise.
  6. Embed. Full uses text_full, B2 text_b2, B1+ none. The client comes from embed.factory() (lazy, cached, one call at a time under a lock). Its identity is checked against the loaded vector meta with check_same_embedding; a difference is embedding_mismatch (409). Client errors become embedding_failed (as built: the message is generic and names only the exception type, never its text). Without embed: capability_unavailable with embed_reason, except for B1+. As built, for a text query the embed capability is checked before the LLM call, so a request that cannot be ranked does not spend a structuring call.
  7. Rank. Full and B2: topk_from_blocks(matrix_block(q, other_side_vectors), 1, n, k). B1+: b1plus_score(resume_doc, posting_doc, weights) for each document of the other side, then the same stable top-k, so ties break by document position everywhere (RT-2).
  8. Notes. no_skills when the final skill list is empty; sparse_query when incomplete_reason is set and skills are non-empty; unknown_skills when every skill is under Other and there is at least one; relabel_mode_differs when the corpus summaries say relabel_mode == "llm" (the query was labeled lookup-only); as built this note is added to form and text queries only, never to corpus queries.
  9. Concurrency. One lock serializes lazy embedder construction and embed(); structuring calls may overlap.

Open questions

Assumptions

A-1 (scope). "An agent explains each match" is delivered as the evidence plus a deterministic, rule-based explainer behind the Explainer protocol (ADR-16), because the LangGraph agent is the separate, unspecced match-agent feature. Chat follow-ups and blind labeling are out of this spec. Not taken: building a small LLM explainer here (it would duplicate match-agent, need a model that must differ from the judges, and not be faithful by construction).

A-2 (query-time labeling). New documents are labeled lookup-only: unseen skills go to Other. If the corpus was relabeled with the LLM, a note says so. Not taken: running the LLM relabeler per query (extra latency and cost, a cache directory to manage). Revisit if trial results show many unseen skills in pasted resumes.

A-3 (input formats). Paste or .txt/.md files only. PDF and DOCX parsing would add a dependency and server-side file handling; a resume PDF can be copied as text. Not taken: pypdf upload.

A-4 (stack). React 18 in plain JavaScript, hash routing, no UI kit (ADR-17). Not taken: Jinja or htmx (one toolchain, but the proposal and presentation promise React) and TypeScript (friction for a small team). Version numbers are not pinned here; package-lock.json pins them at implementation time, and React 19 is acceptable if the testing libraries support it.

A-5 (theme). Values marked "team" in the Theme tokens section are our decisions where the brand guide pages reached by the researcher gave no value (button radius and variant colors, focus ring, heading scale, card and alert styling, hover color, footer wording). The approved color-pair graphic of the guide was not readable, so contrast pairs were chosen by computed WCAG ratios. If the instructor or team obtains the Figma UI kit, only tokens.css and the style-rule test change.

A-6 (logos). The app uses a text wordmark and no ASU mark, per the guide's limits for student projects. Confirm with the instructor if an ASU or School of Computing logo is wanted; that would need written permission and a new ADR.

A-7 (upstream names). Names of modules from draft specs (taxonomy, relabel, docembed, embed, retrieval) are taken from those specs as written on 2026-11-07. If their build changes a name, the web-app task adapts and reports it.

A-8 (embedding health). The embedding capability reports "available" if configured, without loading the model at startup; a missing GPU shows up on the first form or text query as capability_unavailable with the reason. Not taken: loading at startup (slows every demo and breaks corpus-only use).

A-9 (B1+ weights). B1+ at query time uses DEFAULT_WEIGHTS or --b1plus-weights; wiring tuned weights from the evaluation stages is a later change.

Questions for the user

None block the build. Worth confirming: (1) the "Q-1" answer in ADR-15, namely that the demo runs on a team member's machine with their own key; (2) whether a real ASU or SCAI logo is wanted (A-6); (3) whether the old index wording "chat" belongs to match-agent (A-1).
