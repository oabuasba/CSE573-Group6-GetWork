Candidate display names

Find Candidates cards show a deterministic placeholder name, clearly labeled, because the resume corpus has no names.

Status: draftUpdated: 2026-11-14Pipeline step: appMaster: architecture.html
candidate-display-names

Goal

The Find Candidates page lists resumes as bare job titles and levels, which reads as an anonymous list. The resumes are Indeed scrapes with no candidate names (a name appears in about 0.6% of a ~2,000 sample), so the user decided to show a fake name per candidate, generated at display time, and to record that as a limitation (ADR-40). This feature adds a pure, offline generator keyed on the resume id, returns the name on POST /api/match responses only, renders it on candidate cards with a visible "Demo name" tag and one explanatory note, shows "Contact not available in dataset" instead of contact details, proves by tests that the name never reaches artifacts, embeddings, rankings, the chat agent or the evaluation (CC-21), and documents the limitation. It serves the web app (app step) and changes no pipeline stage.

Scope

In scope

  • New module getwork.webapp.pseudonym with display_name(doc_id) and two fixed name lists.
  • One new optional field, Match.display_name, filled by api.py for resume matches only.
  • Candidate cards (MatchCard, resume side): name heading, "Demo name" tag, job title, level, "Contact not available in dataset". One note per results list on the Find Candidates page. The same card on the chat page shows the name and tag (no second note).
  • Tests that enforce the isolation rules of CC-21 (source scan, prompt capture, ranking equality, schema checks).
  • The limitation recorded in docs/deviations.md (P-22) and the web app runbook. The architecture entries (ADR-40, CC-21, CC-18 addition, feature index row) are already written.

Out of scope

  • Any change to ModelOutput / the extraction schema (CC-1), any re-run of the structurer or later stages, any change under data/ or artifacts_trial/.
  • Real names, emails, phones, LinkedIn or other links extracted by regex from resume text. A possible follow-up only; it needs its own spec, a precision measurement and a privacy decision.
  • A location line (see Open questions, assumption A-1): no served artifact carries a location.
  • Names on Find Jobs cards, on the example picker, in the "What we understood" card, in /api/explain or in chat replies. The chat agent is not told the name.
  • Anything under src/getwork/evaluation/ (mid-build); this feature only adds a test that scans it read-only.
  • Unique names. Two resumes may get the same name.

Design

The generator is a pure function of the document id and a fixed seed. api.py calls it while building each Match of a /api/match response, after the engine has already ranked, so the engine, the explainer, the agent and the evaluation never see a name. The React card renders it. Depends on ADR-40, CC-21, CC-18 (the Match shape is extended additively), CC-10 (offline tests, import guards) and the existing front-end conventions (reuse chip chip-other and Notice; no new CSS).

Interfaces

I-1 Generator, new file src/getwork/webapp/pseudonym.py. It imports only hashlib (and __future__); no file, network, clock, random or environment access.

NAME_SEED: str = "getwork-demo-names-v1"
FIRST_NAMES: tuple[str, ...]   # at least 150 distinct entries, each matching ^[A-Z][a-z]+$
LAST_NAMES: tuple[str, ...]    # at least 150 distinct entries, each matching ^[A-Z][a-z]+$

def display_name(doc_id: str | None) -> str | None:
    """Placeholder name "First Last" for a document id, or None when doc_id is None or blank.

    Not blank means doc_id.strip() != "". The id is hashed exactly as given (no strip, no case fold):
        digest = hashlib.sha256(f"{NAME_SEED}:{doc_id}".encode("utf-8")).digest()
        first = FIRST_NAMES[int.from_bytes(digest[0:4], "big") % len(FIRST_NAMES)]
        last = LAST_NAMES[int.from_bytes(digest[4:8], "big") % len(LAST_NAMES)]
        return f"{first} {last}"
    Never raises for a str; never reads anything but its argument and the module constants."""

The lists are a mix of common given names and common surnames, ASCII letters only, written as plain tuple literals, no real-person combinations on purpose (the combination comes from the hash). Python's built-in hash() must not be used (it is salted per process).

I-2 API model, src/getwork/webapp/models.py: add one field at the end of Match; nothing else in the file changes (in particular DocumentView, ExamplesResponse, Explanation and agent models stay as they are):

class Match(BaseModel):
    rank: int  # 1-based
    id: str
    score: float
    document: DocumentView
    evidence: Evidence
    display_name: str | None = None   # NEW: placeholder name, resume matches only (CC-21); None otherwise

I-3 API wiring, src/getwork/webapp/api.py, inside match() where models.Match(...) is built (add pseudonym to the from getwork.webapp import ... line):

display_name=pseudonym.display_name(document.id) if document.side == "resume" else None

Resume matches occur exactly when direction == "posting_to_resume", so job matches always carry "display_name": null. No other file in src/getwork may import pseudonym or mention display_name (AC-10).

I-4 UI copy and card contract, new file src/web/src/candidateCopy.js:

export const DEMO_NAME_LABEL = "Demo name";
export const CONTACT_UNAVAILABLE = "Contact not available in dataset";
export const UNNAMED_CANDIDATE = "Unnamed candidate";
export const NAMES_NOTE =
  "Candidate names are placeholders. The resume dataset has no names, so each name is generated from the resume id and is the same every time.";

MatchCard keeps its props { match, system, expanded, onToggle, children }. A card is a candidate card exactly when match.document.side === "resume". Job cards (side === "posting") are rendered exactly as today. A candidate card renders, in this order inside the existing <article className="card"> (add attribute data-candidate):

<p>Rank {match.rank}</p>
<h3>{name}</h3>                                   // name = match.display_name when it is a non-blank string, else UNNAMED_CANDIDATE
{hasName && <p><span className="chip chip-other" data-demo-name>{DEMO_NAME_LABEL}</span></p>}
<p>{match.document.title || "Untitled"}</p>      // job title, a paragraph (the heading is the name)
<p>{match.document.level}</p>
<p>{CONTACT_UNAVAILABLE}</p>
... score line, EvidenceChips, "Why this match?" button and region: unchanged

The fallback (no usable display_name) shows Unnamed candidate with no tag, because nothing was generated and the tag labels a generated name. The contact line is always rendered on a candidate card and is a plain paragraph: no link, no mailto:, no tel:.

FindPage Results renders, directly after the "N candidates found" paragraph and before the "What we understood" card, exactly one <Notice kind="warning" label="Note">{NAMES_NOTE}</Notice> when response.direction === "posting_to_resume" and matches.length > 0; otherwise none. The chat page card (FocusMatch reuses MatchCard) therefore shows the name, tag and contact line but not the note.

Data flow

Request (posting_to_resume) → engine.match ranks resume ids (unchanged, never sees a name) → api.match() builds each Match, adding display_name from the resume id → JSON → postMatch → FindPage state and the sessionStorage results snapshot (so the name survives a round trip to the chat page; it is transient browser state, not an artifact) → MatchCard. The chat request built by useChat carries query (a DocumentView), focus_id, matches refs {id, rank, score}, history and message; none contains the name, and no change is needed there.

Acceptance criteria

Each criterion states an observable behavior and the test that proves it. Python tests run with uv run --offline --frozen pytest -q and use the demo engine and FakeLLMClient only (CC-10); front-end tests run with npm --prefix src/web test.

  1. AC-1: Determinism. display_name("r-123") returns the same string on repeated calls, and two separate interpreter processes started with different PYTHONHASHSEED values print the same name for the same id. Test: src/tests/webapp/test_webapp_pseudonym.py::test_same_id_same_name, ::test_stable_across_processes (subprocess).
  2. AC-2: The mapping is pinned. The names for r-1, r-2 and r-30000 equal literals written in the test, so any change to the seed, the hash recipe or the lists fails the test and must be a deliberate update. Test: test_webapp_pseudonym.py::test_golden_names.
  3. AC-3: Name shape and spread. Every name matches ^[A-Z][a-z]+ [A-Z][a-z]+$; both lists have at least 150 entries and no duplicate within a list; over ids r-1 to r-2000 at least 1,800 distinct names occur. Test: test_webapp_pseudonym.py::test_name_shape_and_spread.

Open questions

Assumptions

A-1 (location is not shown). The request asks for title and location on the cards. No served artifact carries a location: the structured record has only title, skills, experience (role, company, duration) and education, the documents table (CC-16) has no location column, and DocumentView has none. The city appears only inside the raw resume text under data/processed/, which the engine does not load and developers may not read. Getting it means either changing the extraction schema and re-running (ruled out) or parsing the first lines of raw text with a regex at engine load time (new dependency of the web app on data/processed, unmeasured precision, a new DocumentView or Match field and a privacy decision). I assumed the cards show job title and level only and that location is a follow-up. If the user wants location now, say so and it becomes a separate spec (suggested name candidate-location) that measures the regex on the ~2,000 sample first; it does not change anything in this spec.

A-2 (list size and name format). 150 first and 150 last names, "First Last", ASCII only. A larger list lowers collisions, a smaller one is easier to review; 22,500 combinations is ample for a demo.

A-3 (fallback has no tag). A resume match with no usable name shows "Unnamed candidate" with no "Demo name" tag, because the tag labels a generated name. The alternative (always show the tag) would label something that is not a name.

A-4 (field on Match, not DocumentView). Chosen so that every path that already carries a DocumentView (chat requests, agent prompts, the explain query) cannot carry the name. The alternative, a field on DocumentView, would put the name into the agent prompt builder's input objects and the front end's chat request.

A-5 (index status). The architecture feature index row says proposed as the user asked, although a spec now exists; move it to draft or approved when the user decides. ADR-40 is recorded as accepted because the user made the decision.
