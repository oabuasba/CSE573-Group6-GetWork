Home landing page

A product-style Home page becomes the default route of the web app: a hero with the value proposition and calls to action into the two Find pages, a four-step "how it works", a short list of benefits, an honest "what it is and is not" note, and a closing call to action. Front end only.

Status: draftUpdated: 2026-11-11Area: web UI (src/web)Master: architecture.html
home-landing-page

Goal

Today the app opens straight on the "Find jobs" form, with no explanation of what GetWork is or why a visitor should use it; the only explanation is the About page, which is a reference document (ranking methods, skill clusters, capabilities, privacy). This feature adds a landing page in the style of a product or service site, at the default hash route, that states the premise (two-way matching of resumes and postings that understands related skills and explains each match), shows how it works in four steps, lists what the visitor gets, says plainly what the project is and is not, and sends the visitor into the Find pages. The About page stays as the reference page and the Home page links to it. No backend, API, or model call is added, so it works unchanged in the npm run dev mock server and in uv run webapp serve.

Current state this spec starts from (HEAD a134252): src/web/src/routes.js has ROUTES = ["jobs", "candidates", "about", "chat"] and parseRoute falls back to "jobs", so an empty hash, #/ and any unknown hash show Find jobs. Layout.jsx has three nav links and a span.wordmark. The Find pages live at #/jobs and #/candidates already, so nothing needs to "move" for Find.

Scope

In scope

  • A new route home (hash #/home, also the empty hash, #/ and any unknown hash) rendered by a new HomePage component, with the copy and structure in Design.
  • A "Home" link first in the main navigation, and the wordmark becoming a link to Home.
  • Theme additions for the hero (tokens, contrast pairs) and a home.css file; a small global fix so anchors styled as buttons are not underlined.
  • Scrolling to the top when the route changes (needed because the page is long and the Find pages are reached from its lower buttons).
  • Updating the existing tests that assume the default route is Find jobs, adding tests for the new page, and short runbook notes.

Out of scope

  • Any change under src/getwork/, to /api/*, to dev-mock.js or vite.config.js. No new endpoint, no model or Voyager call.
  • Images, illustrations, icons, screenshots, animations, external fonts or any asset fetched from another site (see A-3). Live metrics or counts (the page makes no request).
  • A router library, real URL paths, server-side redirects, page titles per route (document.title), and focus management on route change.
  • Changing the About page, the Find pages, the chat page or the API contract. Deep links that pre-select a Find input method.
  • The evaluation (planned work); the page must not present results as evaluated (AC-7, AC-9).

Design

Depends on ADR-17 (plain-JavaScript React, hash routing, no router, no UI kit), ADR-18 (theme tokens from public brand values, no ASU marks or code), ADR-15 (stateless local server) and ADR-30 (explanations rules-based, chat only with the agent). Adds ADR-32 (Home is the default route). All files are under src/web/src unless noted. Facts in the copy come from README.md, docs/running-end-to-end.md, specs/architecture.html (Overview, Pipeline), pages/AboutPage.jsx and components/QueryForm.jsx.

Decisions

IdDecisionWhy
H-1Home is the default route; Find keeps #/jobs and #/candidates. parseRoute returns "home" for the empty hash, #/, #/home and any unknown first segment. Nothing else about the route table changes. (ADR-32)A landing page nobody lands on is pointless; Find has its own hash routes already, so no URL needs to move and old bookmarks (#/jobs, #/about) keep working.
H-2Navigation order: Home, Find jobs, Find candidates, About. The wordmark is also a link to Home (outside the nav, so the "exactly one aria-current in the nav" rule still holds). The footer "Contact the team" link still goes to About.Conventional product-site navigation; a visitor on any page can get back to the explanation.
H-3The About page is unchanged and stays the reference page. Home explains the idea at a glance and links to About for the three ranking methods, skill clusters, capabilities and privacy detail. Home does not repeat that detail.Two pages with one job each; avoids two copies of the methods text drifting apart.
H-4Home is static. HomePage takes no props, reads no health data and makes no request. It still renders inside the same gate as every other route in App.jsx (it appears when /api/health has loaded; while loading the h1 is "GetWork" with "Loading…"; if the server is unreachable the existing alert with Retry shows). Statements about the chat agent are worded conditionally ("where the chat agent is switched on").Keeps one failure path and the existing "health fetched once" behavior; avoids copy that is wrong on a server with chat off.
H-5Text and CSS only. The hero is a rounded maroon band (white text, gold primary button, white secondary button) inside the normal container; the step numbers are CSS counters in round badges. No img, svg, role="img", icon font or background image.The existing footer test asserts the default route contains zero img/[role='img'] elements; ADR-18 forbids ASU marks; nothing external to load keeps it working offline.
H-6No claim the system cannot back. No accuracy, speed, superiority or "AI-powered" claims; the page says matching runs against a fixed set of documents (not live listings) and that rankings have not been formally evaluated yet (README: evaluation is "Planned"). Related-skill credit is described as how the default method works ("gives partial credit"), as the About page does.The research question (does the taxonomy beat keyword and embedding baselines) is unanswered; a product page must not answer it early.
H-7Scroll to top on route change. App calls window.scrollTo?.(0, 0) in a useLayoutEffect keyed on route only.Hash links to #/jobs do not match any element id, so the browser would keep the scroll offset of the long Home page and open the Find page at its bottom. A layout effect runs before the passive effect in FindPage that focuses the chat link on "Back to results", so that restore is unaffected.
H-8Anchors styled as buttons are not underlined. One rule a.btn, a.wordmark { text-decoration: none; } in components.css. Today an a.btn (for example "Chat about this suggestion") gets the browser's default underline because only main a:not(.btn) is styled.The hero and closing calls to action are links (they navigate), not buttons. The existing style test allows underline only on link selectors, so none is the safe direction.

SlotExact text
Hero h1Match resumes to jobs, and jobs to resumes
Hero leadGetWork ranks job postings for a resume, or candidates for a posting, by comparing skills, job titles and experience levels. Its default method gives partial credit to related skills, such as React and Vue, and every match comes with the reasons behind it.
Hero primary link (to #/jobs)Find jobs for my resume
Hero secondary link (to #/candidates)Find candidates for a posting
Hero hintNo resume or posting at hand? Choose "Pick an example" on the next page.
How it works introFour steps from a document to a ranked list.
Step 1 h3 / pShare a resume or a posting / Paste the text, fill in a short form, or pick an example. Use Find jobs when you have a resume, and Find candidates when you have a posting.
Step 2 h3 / pGetWork reads it / A language model reads pasted text and pulls out the title, skills and experience. Spellings of the same skill are merged, so JS and JavaScript count as one, and each skill is placed in a skill cluster, a named group of similar skills such as Front-end. Which input options are available depends on how the server was set up, and the page tells you when one is not.
Step 3 h3 / pIt finds the closest matches / Each document becomes a list of numbers, an embedding, that captures its meaning and is built from the title, level and skills grouped under their cluster names. GetWork compares your document with every document on the other side and lists the highest scores first.
Step 4 h3 / pYou see why, and can ask more / Every match lists the skills you share, the related skills and the missing ones, with a short summary written from those lists by rules. Where the chat agent is switched on, you can open a chat about one suggestion; its answers are checked against the two documents before they are shown.
Benefits h2What you get
Benefit 1 h3 / pBoth directions / Job seekers get ranked postings for a resume. Recruiters and hiring managers get ranked candidates for a posting.
Benefit 2 h3 / pRelated skills earn partial credit / A resume that lists Vue can still earn credit against a posting that asks for React when both skills sit in the same cluster, such as Front-end. Which skills share a cluster depends on the data.
Benefit 3 h3 / pReasons you can read / Shared, related and missing skills are listed for every match, with a summary in plain language, so you can see what lines up and what is absent.
Benefit 4 h3 / pChoose how matches are scored / Switch between the skill-cluster method, embeddings only and keywords only to see what each one adds. The About page explains all three.
Benefit 5 h3 / pAsk follow-up questions / Where the chat agent is switched on, ask about one suggestion, for example which skills are missing. Claims that cannot be checked against the two documents are left out.
Benefit 6 h3 / pNothing kept on the server / The server keeps no history and writes nothing. Pasted text goes to the language model only so it can be read, and your results and chats stay in this browser tab until you close it.
Honest h2What GetWork is, and is not
Honest p 1GetWork is a CSE 573 course project at Arizona State University, built by Group 6. It is not an official ASU website and it is not a job board.
Honest p 2It matches against a fixed set of resumes and job postings collected for the project from public data sets (a small built-in sample in demo mode), not against live listings. How well its rankings agree with human judgement has not been formally evaluated yet, so treat the results as suggestions to look at, not as decisions.
Honest p 3The ranking methods, skill clusters and privacy details are on the About page.
Closing h2Ready to see your matches?
Closing pStart with a resume or a posting.
Closing primary link (to #/jobs)Try it with your resume
Closing secondary link (to #/candidates)Try it with a job posting

Heading levels in document order are therefore exactly [1, 2, 3, 3, 3, 3, 2, 3, 3, 3, 3, 3, 3, 2, 2]. Link texts are unique on the page (the two "About page" links go to the same place and may repeat). The words "Voyager" and "ASU Voyager" are not used; the page says "a language model".

Edge cases & risks

  • Old bookmarks and links. #/jobs, #/candidates, #/about and #/chat/<id> behave as before. Only the empty hash and unknown hashes change (Find jobs becomes Home). ChatPage still links to hrefFor("jobs") and hrefFor("candidates"); leave those.
  • Server down on first load. The Home route shows the existing unreachable alert instead of the page (H-4). A visitor with uv run webapp serve not running therefore sees the same message as before; this is deliberate (A-2).
  • Long page, short destination. Without H-7 the Find page would open scrolled down. The layout effect must be keyed on route only, so opening a chat for another match does not jump the page.
  • Hero colors. Maroon with white text and a gold button are allowed brand pairs; gold with white and gray-1 with maroon are forbidden (see pairs.js). Do not set any text in the hero to --text, and do not put a plain (non-button) link in the hero.
  • Counter badges. content: counter(...) / "" is ignored by older browsers; the preceding plain content: counter(...) declaration keeps them working (a screen reader may then read the number twice, which is harmless).
  • Reduced motion. The global prefers-reduced-motion rule already removes the button hover scale; add no new animation.
  • Copy drift. The copy is vetted against the README and the About page. If a later feature changes what the system does (for example the evaluation finishes, or explanations become model-written), update I-6 and AC-5 to AC-9 together.
  • Stale build. webapp serve serves src/web/dist; the user must rebuild (npm --prefix src/web run build) to see Home. The mock dev server needs no rebuild.
  • Two links named "About page". Both go to #/about; tests must use getAllByRole for that name.

Open questions

Assumptions

A-1 (what "the root route" means). The app uses hash routes and there is no separate "/" for Find: Find jobs was only the fallback of parseRoute. Home becomes that fallback, so an empty hash and any unknown hash show Home. Find does not move. If you would rather keep unknown hashes on Find jobs and make only the empty hash show Home, say so; it is a two-line change to parseRoute and AC-1.

A-2 (health gate). Home waits for /api/health like every other route, so the same loading and "cannot reach the server" states apply. The alternative, a landing page that renders even when the server is down, is rejected here because its buttons would lead to a failing page and it would add a second failure path.

A-3 (visuals). No illustrations or screenshots. The look comes from a maroon hero band, numbered badges and cards, using only brand tokens. The existing footer test forbids images at the default route, and ADR-18 forbids ASU marks. If you want an illustration or a product screenshot later, it needs its own spec (and a decision on that test).

A-4 (tone and copy). Plain, second-person, no superlatives, and every capability phrased the way the README and the About page phrase it. The copy in I-6 is final unless you edit it; any rewording must keep AC-7 and AC-9 true.

A-5 (chat wording). The page does not read health.chat; it says "Where the chat agent is switched on". Showing or hiding those lines from health is possible but adds a prop and a second set of copy to test.

A-6 (side effects). The wordmark becomes a link, and the button-link underline rule also removes the browser's default underline from the existing "Chat about this suggestion" link (and any other a.btn). The scroll-to-top applies to every route change, not only from Home.

A-7 (status word). The feature index uses draft for a spec that awaits approval (the vocabulary in architecture.html), not "planning".

Questions for the user

None block the build. Worth confirming: (1) A-1, that unknown hashes should land on Home; (2) A-3, text and CSS only with a maroon hero band; (3) the copy in I-6, in particular the honest note's sentence that rankings have not been formally evaluated yet.
