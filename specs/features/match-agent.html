Match agent

A LangGraph agent that explains each match and answers follow-up questions, where every claim it shows has been checked against tool-produced facts and the two documents' final skill sets, and a plain-language error when it cannot be verified.

Status: draftUpdated: 2026-11-08Pipeline step: 8Master: architecture.html
match-agent

Goal

Step 8 of the pipeline turns a ranked match into an explanation a candidate or recruiter can act on, and lets them ask why one result outranks another. web-app already shows deterministic evidence (shared, related-by-cluster and missing skills) and calls an Explainer through a seam (ADR-16); this feature supplies the agent behind that seam and the chat the web-app deliberately left out. The agent is a small LangGraph state machine that asks an LLM, through the existing LLMClient, to either call one of four read-only tools or give an answer. An answer is a list of claims, and each claim names the documents it is about, the skills it mentions, and the fact ids it rests on. A deterministic verifier then checks every claim against the facts the tools produced and the final skill sets of the documents; a claim that cannot be verified is sent back to the model with the reason. If the agent still cannot give a verified answer, or the model fails or runs out of time or budget, the user sees a short plain-language error with a suggestion of what to try, and no explanation text at all: the agent never silently swaps in the rules-based text, and never shows unverified text (ADR-20). The rules-based explainer is still available as the separate, default --explainer template mode, and the evidence chips on every match card are unaffected by an agent failure. The same structure is what the later evaluation needs: every result carries its claims, skills, fact references, tool trace, status and failure reason, and model identity, so the automatic hallucination rate (a skill named that is in neither document) and the 1 to 5 faithfulness and usefulness ratings can be computed without re-running or parsing prose. LangGraph is kept because the proposal names it, and is an optional extra imported lazily (ADR-19); by default the agent uses the same Voyager backend and model as structuring (ADR-21); tests use FakeLLMClient only.

Scope

In scope

  • Package getwork.agent: grounded-answer models (CC-19), failure copy and AgentFailure, fact builders, four tools, the verifier and the named-skill scan, the prompt and action parser, the turn logic, the LangGraph wiring, AgentExplainer, ChatService, the POST /api/chat route with the failure handler, and a skill vocabulary loader.
  • Additive changes to web-app code: Explanation gains optional claims and facts, ExplainerInfo gains optional backend and prompt_version, webapp serve gains --explainer agent and agent options, the web-app contract fixture gains explain_agent, chat and chat_error, and describeError gains a title for the new error code. No web-app spec or task text is edited; the tasks here modify files that web-app tasks create, after those tasks merge (see Frontend).
  • Frontend: postChat, a shared ClaimList with a per-claim evidence disclosure, the useChat hook, ChatPanel inside the expanded match card, and the plain-language error display, all themed with the existing web-app tokens.
  • What evaluation will read: AgentResult (status, failure reason, claims, facts, trace, usage, model, backend, prompt version), AgentResult.as_record(), and the pure functions named_skills and ungrounded_skills.

Out of scope

  • The evaluation itself, which is on hold: sampling and pooling, the judges and their rubrics, computing the hallucination rate or ratings over a test set, ranking metrics, taxonomy validity. This feature only guarantees the data they will read.
  • Streaming tokens (ADR-20), server-side conversation storage, accounts, rate limiting across users.
  • Any automatic fallback to the rules-based explanation when the agent fails, or a button that shows it (assumption A-6). The rules explainer is a separate server mode.
  • Native OpenAI function calling and LangChain model wrappers; tools use a JSON action protocol over LLMClient.complete (ADR-19).
  • Browsing the raw resume or posting text: the agent sees only structured fields (title, level, skills with clusters), never the free text, so there is no prompt-injection path through uploaded documents beyond skill strings.
  • A CreateAI-specific client or default. The agent is served by Voyager by default (ADR-21); any OpenAI-compatible server, including CreateAI, stays reachable through --agent-backend local and LOCAL_LLM_BASE_URL.
  • Rewriting a user's resume, career advice, or any claim about content outside the skills, level and title of the documents.

Design

Cites ADR-10 (hosting clause superseded by ADR-21), ADR-13, ADR-16, ADR-17, CC-10, CC-18, and adds ADR-19 (LangGraph state machine over a JSON action protocol, optional extra), ADR-20 (verification gate, plain-language failures, stateless chat, no streaming), ADR-21 (agent served by Voyager by default) and CC-19 (grounded answer, chat and failure contract). Requires web-app T-1 (models), T-3 (build_evidence, TemplateExplainer), T-4 (Engine, EngineError, DemoEngine), T-5 (app and error envelope), T-9 (CLI) and the frontend tasks T-13, T-16, T-17; the built getwork.llm package (LLMClient, FakeLLMClient, complete_validated, call_with_retry, make_client) and getwork.alias; and skill-taxonomy T-2 (load_taxonomy) for the artifact vocabulary.

Graph, state and flow

            +------+   action=tool    +----------+
 start -->   |decide|----------------->| run_tool |--+
            +--+---+                  +----------+  |  (adds facts, trace)
               ^  |action=answer                    |
               |  v                                 |
               |+------+  violations, retries left  |
               +|verify|<---------------------------+---- (decide again)
                +--+---+
                   | ok / off_topic            LLM failure, timeout, budget,
                   v                           unverified after retries
               +--------+                      +--------+
               | finish |                      |  fail  |
               +---+----+                      +---+----+
                   v                               v
                  END                             END

Turn holds: the question, trimmed history, the focus pair and scope documents, the facts dict, the tool trace, counters (tool_steps, verify_retries, CallStats), the pending action, the last feedback text, the start time, the failure reason, and the final AgentResult. decide checks budgets first (time, LLM calls), builds the prompt, calls complete_validated(..., parse=parse_action, max_attempts=min(3, remaining calls)), and routes by the parsed action. A tool request beyond max_tool_steps is answered with feedback "No more tool calls are allowed; answer now." and counts against the call budget. verify runs verify_claims; an off_topic answer skips verification and finishes with a fixed reply. Failure reasons map as: FatalLLMError to model_rejected; RetriesExhausted to llm_unavailable; ValidationExhausted to invalid_reply; clock over timeout_s to timeout; LLM-call budget used up to budget_exhausted; verify retries used up to unverified. A failed turn builds an AgentResult with status "failed", no claims and the reason; it is the explainer or chat service that turns it into AgentFailure.

Fact sentences (exact, code-generated)

Document references are query for the user's document and the corpus id otherwise. Roles "the resume" and "the posting" come from DocumentView.side.

  • shared_skills: Shared skills: A, B, C. (all names, in posting order; doc_ids query and match)
  • related_skills (one per group): Related through {cluster}: the resume lists {r1, r2}; the posting asks for {p1, p2}.
  • gap_skills: Skills the posting asks for that the resume does not show: X, Y.
  • level: Experience levels: resume {r}, posting {p} ({relation}).
  • title_overlap: Shared title words: a, b.
  • document_skills: Skills of {ref} ({title}, {level}) by cluster: {C1}: a, b; {C2}: c; Other: d. (title "Untitled" when none)
  • rank_score: {id} is ranked {rank} with {label} {score:.3f}. where label is similarity for Full and B2 and keyword score for B1+
  • comparison: {a} vs {b}: shared with {a} only: {..}; shared with {b} only: {..}; gaps only for {a}: {..}; gaps only for {b}: {..}. (an empty list prints none)
  • cluster_members: In {cluster}: {ref1}: s1, s2; {ref2}: s3.

API shapes and failures (CC-19)

POST /api/chat takes a ChatRequest and returns a ChatResponse (200) only when the agent produced a verified answer or an off-topic reply. Request errors use the web-app envelope: 422 invalid_request for limit violations, 404 not_found for an unknown focus_id or result id, 400 side_mismatch if the focus is on the query's own side. If the app was built without an agent the route is not registered, so the web-app JSON 404 not_found envelope is returned. POST /api/explain keeps the web-app request and response shapes; with the agent explainer its Explanation additionally carries claims and facts. The health response is unchanged: the UI shows chat when health.explainer.kind == "agent".

Agent failure, for both routes: HTTP 502, body {"error": {"code": "assistant_failed", "message": ..., "hint": ..., "field": null}}, the web-app ErrorEnvelope (its code is a plain string). assistant_failed is the only error code this feature adds. It lives in getwork.agent (not in web-app's closed ERROR_CODES table, so web-app's tests are unaffected); the handler for AgentFailure is installed by register_chat_routes on the app, so /api/explain gets it too. message and hint come from this table by failure reason; the reason itself is not in the body, only in the redacted server log (agent failed: reason=timeout, with no message text).

Wording rules (tested): plain, non-technical sentences that end with a period; message says what happened, hint says what to try; at most 100 characters in message; no digits, no status codes, no stack traces, no URLs, no model names, no secret values, and none of the words error, exception, traceback, http, api, token, key, llm, json, model. The server never puts exception text, backend responses or the user's message into the body.

Interaction with the rules explainer: without --explainer agent the server uses TemplateExplainer exactly as web-app specifies and has no chat route; an agent failure never produces template text. With the agent on, the evidence chips (shared, related, missing skills) come from /api/match and stay on every card when an explanation or chat request fails.

What the agent exposes for evaluation

  • Per result: status (ok or failed), failure_reason, claims[] (text, doc_ids, declared skills, cited facts), facts[] (id, kind, doc ids, skills, sentence), trace[] (tool, arguments, ok, produced fact ids), usage, and the model, backend and prompt version. HTTP responses carry the same claims, facts, trace and usage for answers (ChatResponse, Explanation); failed results are available to a batch evaluation through explain_detailed and AgentResult.as_record().
  • Hallucination rate (proposal: a skill named that appears in neither document; cluster names do not count): named_skills(claims, vocab) returns the union of declared skills and vocabulary mentions found in the claim texts; ungrounded_skills(claims, docs, vocab) returns those not in the final skill sets of the given documents. A later evaluation divides by explanations or by named skills. A failed result has no claims and contributes no named skills, so the evaluation must report the error share (failed results over all attempts, by failure_reason) next to the rate.
  • Explanation rating (judges rate faithfulness and usefulness 1 to 5): judges read the claims with their facts and the two documents' raw text; AgentResult.as_record() is the JSON line a batch run would save. Misattributed claims remain a judge's call, but doc_ids makes the intended subject explicit. Failed results are not rated; they are counted in the error share.
  • Verification is on by default and also records verify_retries, so the evaluation can report how often the gate had to intervene.
  • Known limit: the vocabulary scan can only recognise skills in the taxonomy or alias table; a hallucinated skill outside both is still caught by the declared skills rule only if the model declares it. The report must say so.

Open questions

Assumptions

A-1 (tool protocol). Tools use a JSON action protocol over LLMClient.complete, not native function calling (ADR-19). If a later backend offers reliable native tool calls, only prompt.py and turn.decide change.

A-2 (LangGraph). Decided by the user: keep LangGraph because the proposal names it. It is the proposal's choice, not a technical necessity: a four-node loop needs no framework. Swap cost if that changes: replace graph.py with the existing drive function and drop the extra and the dev-group line.

A-3 (agent model host). Decided by the user: the agent is served by Voyager, with the same backend and model as structuring by default, instead of CreateAI as ADR-10 says (ADR-21, deviation P-19). --agent-backend local and --agent-model stay available, so an OpenAI-compatible server (CreateAI included) can be used without code changes. The agent model must still differ from both judge models.

A-4 (no streaming). Responses are whole and verified; the UI shows "Thinking...". Not taken: streaming tokens, which would show unverified text.

A-5 (stateless chat). The client resends history, the query view and the result list each turn; nothing is stored. Not taken: server sessions or checkpointers.

A-6 (failures are errors). Decided by the user: when the agent cannot answer, the user sees a plain-language message and no explanation text; there is no silent fallback to the rules explainer. The wire form is my choice: HTTP 502 with the existing error envelope and one new code, assistant_failed (MA-6). unverified is treated as the same class as model failures. Not taken: a 200 with a message field; a button that shows the rules explanation after a failure (a second code path; the server mode --explainer template serves that need).

A-7 (scope of facts). The agent speaks only about title, level, skills and clusters of the documents in the conversation. Taxonomy-wide questions ("what else is in Front-end?") are out of v1 because they would name skills outside the documents.

A-8 (suggested questions). Generated by rules, not by the model, so they need no verification.

A-9 (web-app files). Tasks here modify files that web-app tasks create, additively, after those tasks merge; no web-app task or AC text was edited. The shared Explanation additions are plain dict fields so the web-app package does not import the agent package. assistant_failed is defined in getwork.agent, not in web-app's closed ERROR_CODES; the only web-app code touched for it is one title in describeError (T-14).

A-10 (evaluation hooks). The agent exposes data and two pure functions only. Choosing denominators, judges, rubrics and sample sizes belongs to the held evaluation features. The report must give the error share by failure reason next to the hallucination rate.
