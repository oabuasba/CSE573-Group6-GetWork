Match agent

A LangGraph agent that explains each match and answers follow-up questions, where every claim it shows has been checked against tool-produced facts and the two documents' final skill sets, with a rules-based answer when it cannot be verified.

Status: draftUpdated: 2026-11-08Pipeline step: 8Master: architecture.html
match-agent

Goal

Step 8 of the pipeline turns a ranked match into an explanation a candidate or recruiter can act on, and lets them ask why one result outranks another. web-app already shows deterministic evidence (shared, related-by-cluster and missing skills) and calls an Explainer through a seam (ADR-16); this feature supplies the agent behind that seam and the chat the web-app deliberately left out. The agent is a small LangGraph state machine that asks an LLM, through the existing LLMClient, to either call one of four read-only tools or give an answer. An answer is a list of claims, and each claim names the documents it is about, the skills it mentions, and the fact ids it rests on. A deterministic verifier then checks every claim against the facts the tools produced and the final skill sets of the documents; a claim that cannot be verified is sent back to the model with the reason, and after two failed rounds the user gets the rules-based answer instead, never unverified text (ADR-20). The same structure is what the later evaluation needs: every response carries its claims, skills, fact references, tool trace and model identity, so the automatic hallucination rate (a skill named that is in neither document) and the 1 to 5 faithfulness and usefulness ratings can be computed without re-running or parsing prose. LangGraph is an optional extra imported lazily (ADR-19); tests use FakeLLMClient only.

Scope

In scope

  • Package getwork.agent: grounded-answer models (CC-19), fact builders, four tools, the verifier and the named-skill scan, the prompt and action parser, the turn logic, the LangGraph wiring, AgentExplainer, ChatService, the POST /api/chat route, and a skill vocabulary loader.
  • Additive changes to web-app code: Explanation and ExplainerInfo gain optional fields, webapp serve gains --explainer agent and agent options, the web-app contract fixture gains a chat section. No web-app spec or task text is edited; the tasks here modify files that web-app tasks create, after those tasks merge (see Frontend).
  • Frontend: postChat, a shared ClaimList with a per-claim evidence disclosure, ChatPanel inside the expanded match card, and the fallback notice, all themed with the existing web-app tokens.
  • What evaluation will read: AgentResult (claims, facts, trace, usage, model, backend, prompt version, source, fallback reason), AgentResult.as_record(), and the pure functions named_skills and ungrounded_skills.

Out of scope

  • The evaluation itself, which is on hold: sampling and pooling, the judges and their rubrics, computing the hallucination rate or ratings over a test set, ranking metrics, taxonomy validity. This feature only guarantees the data they will read.
  • Streaming tokens (ADR-20), server-side conversation storage, accounts, rate limiting across users.
  • Native OpenAI function calling and LangChain model wrappers; tools use a JSON action protocol over LLMClient.complete (ADR-19).
  • Browsing the raw resume or posting text: the agent sees only structured fields (title, level, skills with clusters), never the free text, so there is no prompt-injection path through uploaded documents beyond skill strings.
  • A CreateAI-specific client. CreateAI is OpenAI-compatible, so it is reachable through the existing local backend by setting LOCAL_LLM_BASE_URL (assumption A-3).
  • Rewriting a user's resume, career advice, or any claim about content outside the skills, level and title of the documents.

Design

Cites ADR-10, ADR-13, ADR-16, ADR-17, CC-10, CC-18, and adds ADR-19 (LangGraph state machine over a JSON action protocol, optional extra), ADR-20 (verification gate, stateless chat, no streaming) and CC-19 (grounded answer contract). Requires web-app T-1 (models), T-3 (build_evidence, TemplateExplainer), T-4 (Engine, EngineError, DemoEngine), T-5 (app and error envelope), T-9 (CLI) and the frontend tasks T-13, T-16, T-17; the built getwork.llm package (LLMClient, FakeLLMClient, complete_validated, call_with_retry, make_client) and getwork.alias; and skill-taxonomy T-2 (load_taxonomy) for the artifact vocabulary.

Graph, state and flow

            +------+   action=tool    +----------+
 start -->   |decide|----------------->| run_tool |--+
            +--+---+                  +----------+  |  (adds facts, trace)
               ^  |action=answer                    |
               |  v                                 |
               |+------+  violations, retries left  |
               +|verify|<---------------------------+---- (decide again)
                +--+---+
                   | ok / off_topic            LLM failure, timeout, budget,
                   v                           unverified after retries
               +--------+                      +----------+
               | finish |                      | fallback |
               +---+----+                      +----+-----+
                   v                                v
                  END                              END

Turn holds: the question, trimmed history, the focus pair and scope documents, the facts dict, the tool trace, counters (tool_steps, verify_retries, CallStats), the pending action, the last feedback text, the start time, and the final AgentResult. decide checks budgets first (time, LLM calls), builds the prompt, calls complete_validated(..., parse=parse_action, max_attempts=min(3, remaining calls)), and routes by the parsed action. A tool request beyond max_tool_steps is answered with feedback "No more tool calls are allowed; answer now." and counts against the call budget. verify runs verify_claims; an off_topic answer skips verification and finishes with a fixed reply. Failure reasons map as: FatalLLMError to model_rejected; RetriesExhausted to llm_unavailable; ValidationExhausted to invalid_reply; clock over timeout_s to timeout; LLM-call or tool budget used up to budget_exhausted; verify retries used up to unverified.

Fact sentences (exact, code-generated)

Document references are query for the user's document and the corpus id otherwise. Roles "the resume" and "the posting" come from DocumentView.side.

  • shared_skills: Shared skills: A, B, C. (all names, in posting order; doc_ids query and match)
  • related_skills (one per group): Related through {cluster}: the resume lists {r1, r2}; the posting asks for {p1, p2}.
  • gap_skills: Skills the posting asks for that the resume does not show: X, Y.
  • level: Experience levels: resume {r}, posting {p} ({relation}).
  • title_overlap: Shared title words: a, b.
  • document_skills: Skills of {ref} ({title}, {level}) by cluster: {C1}: a, b; {C2}: c; Other: d. (title "Untitled" when none)
  • rank_score: {id} is ranked {rank} with {label} {score:.3f}. where label is similarity for Full and B2 and keyword score for B1+
  • comparison: {a} vs {b}: shared with {a} only: {..}; shared with {b} only: {..}; gaps only for {a}: {..}; gaps only for {b}: {..}. (an empty list prints none)
  • cluster_members: In {cluster}: {ref1}: s1, s2; {ref2}: s3.

API shapes (CC-19)

POST /api/chat takes a ChatRequest and returns a ChatResponse (200 in every agent outcome, including fallback). Request errors use the web-app envelope: 422 invalid_request for limit violations, 404 not_found for an unknown focus_id or result id, 400 side_mismatch if the focus is on the query's own side, and, if the app was built without an agent, the route is not registered at all, so the web-app JSON 404 not_found envelope is returned. No new error codes are added. POST /api/explain is unchanged; its Explanation gains optional fields. The health response is unchanged: the UI shows chat when health.explainer.kind == "agent".

What the agent exposes for evaluation

  • Per response and per explanation: claims[] (text, doc_ids, declared skills, cited facts), facts[] (id, kind, doc ids, skills, sentence), source (agent or rules), fallback_reason, trace[] (tool, arguments, ok, produced fact ids), usage, and in explainer the model, backend and prompt version.
  • Hallucination rate (proposal: a skill named that appears in neither document; cluster names do not count): named_skills(claims, vocab) returns the union of declared skills and vocabulary mentions found in the claim texts; ungrounded_skills(claims, docs, vocab) returns those not in the final skill sets of the given documents. A later evaluation divides by explanations or by named skills. A rules fallback has no claims and contributes no named skills, so evaluation must report the fallback share next to the rate.
  • Explanation rating (judges rate faithfulness and usefulness 1 to 5): judges read the claims with their facts and the two documents' raw text; AgentResult.as_record() is the JSON line a batch run would save. Misattributed claims remain a judge's call, but doc_ids makes the intended subject explicit.
  • Verification is on by default and also records verify_retries, so the evaluation can report how often the gate had to intervene.
  • Known limit: the vocabulary scan can only recognise skills in the taxonomy or alias table; a hallucinated skill outside both is still caught by the declared skills rule only if the model declares it. The report must say so.

  • Every Python test file starts with pytestmark = pytest.mark.usefixtures("offline") (sockets blocked, VOYAGER_*, LLM_BACKEND, LOCAL_LLM_* unset, cwd = tmp_path). Open questions

Assumptions

A-1 (tool protocol). Tools use a JSON action protocol over LLMClient.complete, not native function calling (ADR-19). If a later backend offers reliable native tool calls, only prompt.py and turn.decide change.

A-2 (LangGraph weight). LangGraph is used as a thin state-machine shell around framework-free logic. The honest alternative is a 40-line loop with no dependency; it was not taken because the proposal, presentation and ADR-10 name LangGraph. Say if you want it dropped: only graph.py and the extra change.

A-3 (agent model host). ADR-10 says the agent model is reached through ASU CreateAI. The shared LLM factory has only the voyager and local backends, so CreateAI is reached as an OpenAI-compatible server through --agent-backend local and LOCAL_LLM_BASE_URL (and LOCAL_LLM_API_KEY if it needs one); no code is added for it. By default the agent reuses the structuring client and model. Not taken: a third backend for CreateAI (until its endpoint and auth are confirmed).

A-4 (no streaming). Responses are whole and verified; the UI shows "Thinking...". Not taken: streaming tokens, which would show unverified text.

A-5 (stateless chat). The client resends history, the query view and the result list each turn; nothing is stored. Not taken: server sessions or checkpointers.

A-6 (fallback is HTTP 200). Model trouble is reported in the body (source, fallback_reason), not as an HTTP error, so the user still gets the evidence. Not taken: 502 responses.

A-7 (scope of facts). The agent speaks only about title, level, skills and clusters of the documents in the conversation. Taxonomy-wide questions ("what else is in Front-end?") are out of v1 because they would name skills outside the documents.

A-8 (suggested questions). Generated by rules, not by the model, so they need no verification.

A-9 (web-app files). Tasks here modify files that web-app tasks create, additively, after those tasks merge; no web-app task or AC text was edited. The shared Explanation additions are plain dict fields so the web-app package does not import the agent package.

A-10 (evaluation hooks). The agent exposes data and two pure functions only. Choosing denominators, judges, rubrics and sample sizes belongs to the held evaluation features.

Questions for the user

None block the build. Worth confirming: (1) keep LangGraph despite its weight (A-2); (2) how the agent model will be hosted (A-3, CreateAI via an OpenAI-compatible base URL, or the same Voyager/local model as structuring); (3) that falling back to the rules answer, rather than showing an error, is the wanted behavior when the model fails (A-6).
