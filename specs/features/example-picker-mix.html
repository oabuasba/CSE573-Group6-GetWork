Example picker mix

The "Pick an example" dropdown on the Find pages shows three fixed examples that are always there, in the same order, followed by three more drawn at random each time the picker is shown. Front end only.

Status: doneUpdated: 2026-11-14Area: web UI (src/web)Master: architecture.html
example-picker-mix

Goal

The user asked: "when clicking on 'pick an example' can we have a default 3 that always present and another random 3 that are different each time?" Today the picker is a native select filled from GET /api/examples?side=<side>&limit=6, and the server answers with the first six documents in id order, so every visit shows the same six. This feature makes the dropdown show six examples in two labelled groups: three fixed "Suggested examples" (the first three the server returns, always in that order) and three "More examples" drawn at random from the next documents, re-drawn each time the "Pick an example" method is shown. It applies to both directions (resumes on Find jobs, postings on Find candidates).

Current state this spec starts from (HEAD a134252, with the uncommitted Home page work in the tree): src/web/src/components/QueryForm.jsx has an ExamplePicker({ side, fetchImpl, chosen, onChoose }) that calls getExamples(side, 6, fetchImpl) in an effect keyed on [side, fetchImpl] and renders one flat select (first option "Choose an example", then one option per item, text {title or "Untitled"}, {level}, {n} skills). ExamplePicker is mounted only while the "Pick an example" method is active, so each click on that method button remounts it and refetches. FindPage renders <QueryForm key={direction} ...>, so a direction change remounts everything and clears the chosen example. src/getwork/webapp/api.py accepts limit from 1 to models.MAX_EXAMPLES (20); ArtifactEngine.examples and DemoEngine.examples both return docs[:limit].

Scope

In scope

  • A new pure module src/web/src/examplePick.js that splits a list of examples into the fixed group and the random group, with an injectable random source.
  • ExamplePicker in QueryForm.jsx fetches 20 examples instead of 6, uses the module, and renders two optgroups (or a flat list when there is nothing to randomize). QueryForm gets an optional random prop for tests.
  • Tests: a unit test file for the module, updated and new QueryForm tests, one new FindPage test, one new accessibility test.

Out of scope

  • Anything under src/getwork/, the /api/examples contract, src/web/dev-mock.js, src/web/src/fixtures/contract.json, the demo engine's documents. No new endpoint, no model or Voyager call (CC-10): every test uses a stubbed fetchImpl and offline data.
  • Drawing from the whole corpus. The random group is drawn from the server's first 20 documents of that side (see E-2 and ADR-34).
  • Replacing the native select with a custom popup, and detecting the moment the browser opens the menu (a native select has no open event).
  • Remembering previous draws so that two draws can never be equal (see E-4), caching the fetched list across mounts, and any change to the Home, chat or About pages.

Design

Depends on ADR-17 (plain-JavaScript React, no UI kit), ADR-29 / ui-polish-3 AC-2 (the example picker is a native labelled select in the one-row control group), and CC-18 (the examples endpoint; unchanged). Adds ADR-34 (client-side mix over a fixed-size pool; server unchanged). All files are under src/web/src.

Decisions

IdDecisionWhy
E-1"Each time" means each time the picker is shown, not each time the browser opens its menu. The mix is computed once, when the examples response arrives after ExamplePicker mounts. That happens on every click of "Pick an example" (the method button remounts the picker), on a direction change, and on a page load. It does not change while the picker stays on screen: choosing an option, changing "Number of results" or "Ranking method", or any re-render keeps the same six.A native select has no open event, and the list must not change under the user's cursor while the menu is open. The user's own words, "when clicking on 'pick an example'", describe exactly this moment. A custom popup would give a real "open" event but would break the native keyboard behavior, user.selectOptions in the existing tests, and the ui-polish-3 decision to use a native control.
E-2The pool is the server's first 20 documents of the side. ExamplePicker requests limit=20 (EXAMPLE_POOL_LIMIT, equal to MAX_EXAMPLES). The fixed group is items 1 to 3 as returned; the random group is drawn from items 4 to 20 (at most 17 items), never from the fixed three, with no duplicates.The server only offers "first N", so a larger client-side pool is the only way to vary the list without changing the API. 17 candidates give 680 possible triples, enough that a repeat is rare. The cost is that documents beyond the 20th are never shown; ADR-34 records the server-side alternative and why it was deferred.
E-3Small pools degrade without padding. Fewer than 3 documents after the fixed group: show all of them, shuffled, in the second group. No documents after the fixed group (3 or fewer items in total): no second group, and the list is flat, without group labels. Fewer than 3 items in total: show what there is. No items: just the placeholder option (as today).Never invent or repeat an item. The labels are only worth showing when there are two groups. The demo engine has 6 documents per side, so demo mode shows the other three in a shuffled order each time (the same three documents); the real artifact corpus gives the full pool.
E-4Independent random draws; "different each time" is statistical, not enforced. No memory of the previous draw. With a pool of 17 two consecutive draws are equal with probability 1/680 (order of the group is ignored in that count); with a pool of exactly 3 (demo mode) the set is always the same and only the order varies.Enforcing a difference needs module-level or storage state and a rule for tiny pools, for a one-in-680 event. Said plainly here so the reviewer does not read it as a defect.
E-5A chosen example stays in the list. If an example is already chosen and it is in the random pool (not the fixed three) when the list is redrawn (the user picks one, switches to "Paste text", comes back), it is pinned as the first item of the random group and the other two are drawn from the rest. If it is one of the fixed three nothing special is needed.Otherwise the select would hold a value that has no option: the browser shows the placeholder while the form state still holds the id, so a submit would send an example the user cannot see.
E-6Randomness is injected. pickExamples takes random (default Math.random, a function returning a number in [0, 1)); QueryForm takes an optional prop random and passes it to ExamplePicker. FindPage is not changed; its tests stub Math.random.Deterministic tests with no timers and no real randomness. The prop and the chosen id are read inside the fetch callback through refs so that a new function identity or a selection never refetches or reshuffles.
E-7Accessibility is native. Groups are optgroup elements with a non-empty label; the labels are "Suggested examples" and "More examples, shuffled". The select keeps its label ("Example resume" / "Example posting" with the required marker), the placeholder stays first and outside both groups, and keyboard and screen reader behavior is the browser's. No live region and no extra focus handling.Native optgroup is announced by screen readers and styled by the browser (including dark mode), so no CSS or ARIA is needed and the one-row control layout is untouched.

I-1 · src/web/src/examplePick.js (new)

export const DEFAULT_COUNT = 3;          // size of the fixed group
export const RANDOM_COUNT = 3;           // size of the random group
export const EXAMPLE_POOL_LIMIT = 20;    // limit sent to /api/examples (= server MAX_EXAMPLES)

/**
 * items:   DocumentView-like objects in server order; only `id` is read here.
 * random:  () => number in [0, 1).
 * chosenId: id of the currently chosen example, or null.
 * Returns { defaults, random } where `defaults` is the first DEFAULT_COUNT items
 * and `random` holds up to RANDOM_COUNT other items. The two arrays never share an id.
 */
export function pickExamples(items, { random = Math.random, chosenId = null } = {})
  // returns { defaults: object[], random: object[] }

Algorithm, exactly (so tests can name expected ids):

  1. Drop items whose id was already seen (keep the first). Call the result list.
  2. defaults = list.slice(0, 3); pool = list.slice(3).
  3. If chosenId is the id of an item in pool: pinned = [that item] and it is removed from pool; otherwise pinned = [].
  4. k = Math.min(RANDOM_COUNT - pinned.length, pool.length). Partial Fisher-Yates on a copy arr of pool, with n = arr.length: for i from 0 to k - 1: j = Math.min(n - 1, i + Math.floor(random() * (n - i))); swap arr[i] and arr[j]. random() is called exactly k times.
  5. random = [...pinned, ...arr.slice(0, k)]. Return { defaults, random }. The input array is never mutated.

Worked values for the tests: items a1..a8 (so defaults are a1, a2, a3 and the pool is a4..a8). With random() always 0 the random group is a4, a5, a6. With random() always 0.99 it is a8, a4, a5. With chosenId "a6" and random() always 0 it is a6, a4, a5 (two calls). For items r-1..r-10 (pool r-4..r-10, 7 items), always 0 gives r-4, r-5, r-6 and always 0.99 gives r-10, r-4, r-5.

Edge cases & risks

  • Pool smaller than expected. Handled by E-3 and AC-2. In demo mode (6 documents per side) the random group is always the same three documents, only their order changes; this is a property of the data, not a bug. The Python demo engine and its tests (health counts 6 and 6) must not be changed for this feature.
  • The server returns fewer items than asked for. limit=20 on a corpus of 6 returns 6 items; nothing special is needed.
  • Payload size. Twenty DocumentViews with their skills are fetched on every click of "Pick an example" instead of six. This is small (tens of kilobytes at most) and the local server is on the same machine. Caching across mounts is out of scope.
  • React StrictMode (development). The effect runs twice and the first run is discarded by the existing live flag, so only the surviving response draws; a draw happens only inside the response callback.
  • Chosen id absent from a later response (the server's data changed between mounts). The select would show the placeholder while the form still holds the old id; a submit then returns the server's not_found error through the normal error path. Not handled specially.
  • Option text is long. Unchanged from today; the select lives in the existing control-row cell (flex: 1 1 12rem; min-width: 0).
  • Existing tests. Tests that use contract.examples (3 items) are unaffected because nothing is randomized with three items; tests that match the fetch path with startsWith("/api/examples") (FindPage.test.jsx, App.test.jsx, a11y.test.jsx) are unaffected by the new query string; the only literal limit=6 to change is in QueryForm.test.jsx. dev-mock.test.js requests limit=6 from the mock, which ignores the query string, and is left alone.
  • The random group is not a statistically fair sample of the corpus. It is drawn from the first 20 documents in id order. Acceptable for picking a demo query; see E-2 and ADR-34.

Open questions

None block the build. Each was resolved by an assumption the user can reverse.

  • Q-A (assumed): "each time" means each time the "Pick an example" method is shown (E-1), not each time the browser opens the menu. If the user wants a fresh list on every menu open, the native select must become a custom listbox, which is a separate feature with its own accessibility work.
  • Q-B (assumed): the random three come from the first 20 documents of the side (E-2). If the user wants them drawn from the entire corpus, the server needs a sampling parameter on /api/examples (see ADR-34, rejected alternative) and this spec's I-1 pool step would move to the server; say so and I will spec it.
  • Q-C (assumed): the fixed three are whatever the server returns first (the lowest ids), not hand-picked "best" examples. If specific showcase examples are wanted, name their ids or the selection rule.
  • Q-D (assumed): group labels read "Suggested examples" and "More examples, shuffled"; wording can change without affecting the design (update AC-5, T-2).
  • Q-E (assumed): a repeat of the previous random three is allowed (E-4).
