UI polish 3: chat page, example dropdown, one-row controls, sticky footer

Chat about a suggestion moves to its own full-page, claude.ai-style window; the example picker becomes a dropdown; the three query controls share one row; the footer sits at the bottom of the viewport on short pages.

Status: draftUpdated: 2026-11-11Area: web UI (src/web)Master: architecture.html
ui-polish-3

Goal

Four user-requested changes to the React front end, all in src/web/src, none touching the HTTP API: (1) choosing "Chat about this suggestion" opens a new page, a full-height chat window for that one match (a conversation thread with user and assistant bubbles, a composer pinned to the bottom, a pending indicator, retry on failure, a way back to the results); (2) the "Pick an example" list becomes a dropdown like the "Number of results" and "Ranking method" selects; (3) those controls sit on one row and wrap on narrow screens; (4) the footer sits at the bottom of the viewport when the page is short and follows the content when it is long. The existing POST /api/chat request and response contract (CC-19) is unchanged.

Current state this spec starts from (commits f077cc8 and 0f303ee): /api/explain is always rules-based and makes no model call; the agent serves only /api/chat; /api/health carries a chat block {enabled, model, backend, prompt_version, reason} (ChatInfo in getwork.webapp.models); the UI shows the chat button when health.chat.enabled === true. Chat failure diagnostics on the server (a developer is adding them under AD-3) are out of scope here.

Scope

In scope

  • A chat page at the hash route #/chat/<match id>: header with a back link, the focus match card with its "Why this match?" content and skills, the message thread, the composer, pending, error and retry states, the disabled-chat and no-session states.
  • Handing data to that page: a sessionStorage snapshot of the last search results (and the expanded card), restored when the user comes back, plus a per-match conversation kept in the same tab.
  • Removing the inline chat (ChatOnDemand.jsx, ChatPanel.jsx and their tests); the result card gets a link to the new page instead.
  • The example picker as a select; the shared one-row control group; the sticky-footer app shell.
  • Tests (Vitest, React Testing Library, jsdom, vitest-axe), the web-app runbook note, and supersession notes in the web-app and match-agent specs.

Out of scope

  • Any change to /api/chat, /api/explain, /api/health or the Python code. Server-side chat failure logging (AD-3).
  • Real token streaming (see ADR-20 and assumption A-3), a new router library, server-side sessions, and restoring the query form fields on return.
  • The npm run dev mock server (dev-mock.js) gaining a chat endpoint; check the chat page against webapp serve.
  • The candidate name or contact idea (deferred, status.json candidate-contact-info).

Design

Depends on ADR-17 (plain-JavaScript React, hash routing, no UI kit), ADR-18 (theme tokens), ADR-20 (verified, non-streamed answers), CC-18 and CC-19. Adds ADR-29. Revises the web-app front end spec (screens, AC-31) and the match-agent front end (AC-24, AC-25, AC-32): see "Superseded text" below.

Decisions

IdDecisionWhy
U-1Routing is the existing hash router. src/web/src/routes.js and useHashRoute in App.jsx parse window.location.hash; there is no router library. The chat page is the route chat with the match id in the hash: #/chat/<encodeURIComponent(id)>. Each hash change is a history entry, so the browser Back and Forward buttons work with no extra code.A router library adds a dependency for one page; the id in the hash makes the URL meaningful and lets the page reject a stale id.
U-2The page gets its data from a sessionStorage snapshot of the last results (key getwork.results.v1): direction, the whole MatchResponse (query view, system, matches, notes) and the expanded card id. The chat page finds the focus match in response.matches by the id in the hash and builds the chat request from the snapshot. A reload of the chat page reads the same snapshot, so it works. If the snapshot is missing or does not contain the id, the page shows a friendly "open this from a result" state.The chat needs the query DocumentView, the ranked list and the system exactly as searched. Re-fetching by id cannot restore them (the query may be pasted text or a form that is not stored on the server); the server is stateless (ADR-15).
U-3Back to results restores the results. The chat page sets a "returning" flag in the snapshot when it mounts. FindPage restores the stored results only when that flag is set and the direction matches, then clears the flag. Plain navigation to Find jobs (from About, or a reload) still starts with an empty page, as today.Going back must not lose a search that took up to a minute; but returning to an old result list every time would be a behavior change nobody asked for.
U-4The conversation is kept per match in the same tab (sessionStorage key getwork.chat.v1:<match id>), so a reload or Back then Forward keeps it. A new search clears all stored conversations. A "Start over" button clears the current one. Nothing is sent to the server except the existing chat requests."Survives a reload as far as reasonable." Per-tab storage is gone when the tab closes.
U-5The inline chat is removed. ChatOnDemand.jsx, ChatPanel.jsx and ChatPanel.test.jsx are deleted. useChat.js, chatHistory.js and ClaimList.jsx stay and are reused. The result card shows a link styled as a secondary button (an anchor, because it navigates) with the same text "Chat about this suggestion".The user wants the button to go to the new page; two chat UIs would diverge.
U-6No streaming. The API returns a whole verified answer (ADR-20, match-agent A-4). The "streaming-like" feel is a pending assistant bubble with a status message while the request is in flight, an immediate user bubble, and automatic scrolling to the newest item. No animation is added (the style-rules test parser does not handle @keyframes).Streaming unverified text would break the grounding guarantee.
U-7Layout of the chat page. The page is a flex column that fills the main area: heading and back link, focus card, the thread (grows), and the composer, which is position: sticky; bottom: 0 inside main. The site footer stays visible below the thread (the composer sticks to the viewport bottom while the thread is long and sits just above the footer when it ends). No fixed positioning, so the composer never overlays content or hides the footer.Robust without height arithmetic; keeps the footer disclaimer and landmarks on every page.
U-8Sticky-footer shell for every page. Layout renders one wrapper div.app-shell (flex column, min-height: 100vh then 100dvh) around the skip link, header, demo banner, main.app-main (grows, width: 100%) and the footer. The footer is a normal flow item after main, so it is at the viewport bottom when content is short and below the content when it is long.Needs only CSS; width: 100% is required because .container has auto side margins, which would otherwise shrink the flex item.
U-9Example dropdown and control row. The three controls use the same Field component and the same select styling. They sit in a div.control-row (flex, wrap). The example select appears only while the "Pick an example" method is chosen; the other two are always present. Wrapping uses flex-basis in rem, no media query: three controls share a row on a wide screen, two then one on a medium screen, one per row on a phone.Simple, testable CSS; matches the existing token and rem rules.

Exact copy and structure

  • Result card link (inside the expanded card, after the explanation, only when health.chat.enabled === true): <a className="btn btn-secondary" href={chatHref(match.id)}>Chat about this suggestion</a>. Never gold. The inline chat panel and its heading "Ask about this match" no longer exist.
  • ChatPage, normal state, in DOM order: a.link "Back to results" (href #/jobs or #/candidates from the snapshot direction); h1 "Chat about this suggestion"; section aria-label="The suggestion" holding h2 "This suggestion" and a MatchCard (the focus match only, expanded false by default; its children are GroupedSkills of the match document and ExplainPanel, as in FindPage); section with h2.sr-only "Conversation" and the ChatThread; the ChatComposer as form.chat-composer. No other match, no "What we understood" card, no results list.
  • Thread: a scroll area div.chat-thread holding div role="log" aria-live="polite" with one div.chat-bubble per turn (.chat-bubble-user aligned right, .chat-bubble-assistant left). Each bubble starts with span.sr-only "You: " or "Assistant: ". An assistant bubble renders ClaimList (claims and facts, each claim keeps its "Show evidence" button), or the reply text in a .measure paragraph when off_topic. After the last bubble: suggested questions of the latest assistant turn as .btn.btn-secondary buttons inside div.chat-suggestions. When there are no turns: a paragraph "Ask anything about why this suggestion fits, or what is missing." and the starters as the same kind of buttons.
  • Pending: while status === "thinking", outside the log region, a bubble div.chat-bubble.chat-bubble-assistant role="status" with the visible text "The assistant is thinking…". The user's bubble is already in the log.
  • Error: while status === "error", Notice kind="error" role="alert" with describeError(error) title, body and hint, and a .btn.btn-secondary "Try again" that calls retry. The user's bubble stays; no assistant bubble is added.
  • Composer: form.chat-composer with a visually hidden label (.sr-only) "Your question" bound to a textarea (placeholder "Ask about this suggestion", maxLength 1000, rows = number of lines in the draft clamped to 1..6), a counter "n / 1000" (.chat-counter), a .btn.btn-primary "Send" (type submit, disabled for a blank draft and while disabled) and, only when there are turns, a .btn.btn-secondary "Start over" (type button, disabled while thinking). Enter sends; Shift+Enter inserts a newline; Enter while an IME composition is active (event.nativeEvent.isComposing) does nothing special.
  • Scrolling: ChatThread ends with an empty sentinel div; after every change of turns or status it calls sentinel.scrollIntoView?.({ block: "end" }) (optional call, because jsdom does not implement it).
  • Focus: on mount of the normal state the textarea gets focus; after an assistant reply and after "Start over" it gets focus again; the textarea is not disabled while the request is in flight (so focus is never lost). In the unavailable and no-session states the h1 (tabIndex={-1}) gets focus on mount.
  • Chat disabled (health.chat?.enabled !== true): h1 "Chat about this suggestion"; Notice kind="warning" label="Chat is unavailable." with the text health.chat.reason or, when it is null or absent, "Chat is not available on this server."; a link "Back to results" when a snapshot exists, else "Go to Find jobs" (#/jobs). No composer, no network call.
  • No session (chat enabled but no snapshot, or the id is null or not in the snapshot's matches): h1 "Chat about this suggestion"; the paragraph "Open a chat from a search result: run a search, open a result with Why this match?, then choose Chat about this suggestion."; links "Find jobs" (#/jobs) and "Find candidates" (#/candidates). No composer, no network call.
  • Example dropdown (replaces the radio fieldset): Field labeled "Example resume" or "Example posting" with the required marker, holding a select whose first option is "Choose an example" (value "") followed by one option per item, text {title or "Untitled"}, {level}, {n} skills, value the item id. While loading: p role="status" "Loading examples…" in the same cell; on error the existing Notice kind="error" role="alert" with the error title. Choosing the placeholder sets the example to none; submitting with none shows "Choose an example first." (unchanged).
  • Control row: div.control-row contains, in DOM order, the example field (only when the example method is active), "Number of results", "Ranking method". All three are Field + select.

Open questions

Assumptions

A-1 (what "Pick an example" means). The "Paste text / Fill in a form / Pick an example" buttons stay as the method switch. What becomes a dropdown is the example list that appears under that method (today a set of radio buttons). The one-row group is therefore: the example select (only while that method is active), "Number of results", "Ranking method".

A-2 (button or link). "Chat about this suggestion" is an anchor styled as a secondary button, because it navigates; screen readers announce a link. Existing tests that looked for a button by that name change to a link.

A-3 (streaming). The page shows a pending assistant bubble, not streamed text. The API returns a whole verified answer on purpose (ADR-20): streaming would show text before it is checked. Changing that is a backend and ADR-20 decision, not part of this spec.

A-4 (starter questions). The empty thread offers two client-side starter questions per direction, written to match the server's own suggestion rules. They are plain constants (STARTERS); the server cannot answer outside its facts either way.

A-5 (restore scope). Coming back from the chat page restores the results and the expanded card, not the text typed into the query form. The form resets, as it does today when leaving the page.

A-6 (conversation storage). Conversations are kept per match in sessionStorage so a reload or Back/Forward keeps them. If you prefer a chat that always starts empty, drop T-5 and the persistence parts of T-8 and AC-16; nothing else depends on them.

A-7 (footer on the chat page). The footer stays on the chat page, below the thread, and the composer sticks to the bottom of the viewport inside main. A chat page without a footer would drop the disclaimer landmark and needs a different layout.

A-8 (match-agent and web-app specs). Those specs still describe the inline chat and the example radios; this spec supersedes them and notes were added there. They also still describe the agent as the explainer; the commits f077cc8 and 0f303ee made explanations rules-based, which this spec follows (health.chat decides whether chat shows).

Questions for the user

None block the build. Worth confirming: (1) A-1, the reading of "Pick an example"; (2) A-6, whether a reload or Back/Forward may keep the conversation (in the browser tab only); (3) A-3, that a pending bubble is acceptable instead of token streaming.
